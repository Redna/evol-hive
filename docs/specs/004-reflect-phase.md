# Feature: Reflect Phase of the PPER Loop

## Context
- Architecture: [§6 — PPER Loop](../architecture/06-pper-loop.md) (Reflect section: System 2 background, consolidate memories, adjust state), [§7 — Structured Outputs](../architecture/07-structured-outputs.md) (schema enforcement), [§8 — Cognitive Tools](../architecture/08-cognitive-tools.md) (`update_internal_state` tool, `UpdateStateResult`), [§11 — Memory Architecture](../architecture/11-memory-architecture.md) (memory storage, MemoryNode, MemoryType), [§3 — Agent State Schema](../architecture/03-agent-state-schema.md) (AgentInternalState, AgentDrives, AgentPlan), [§2 — System Overview](../architecture/02-system-overview.md) (package boundaries)
- Related specs: [001 — Perceive Phase](001-perceive-phase.md) (produces `PerceptionResult`, `PerceptionDataProvider`), [002 — Plan Phase](002-plan-phase.md) (produces `AgentPlan`, `PlanResult`, `PlanDataProvider`), [003 — Execute Phase](003-execute-phase.md) (produces `ExecuteResult`, `ExecuteDataProvider`)
- Package: `shared`, `cognition`, `memory`, `engine`
- ADR: [ADR-0001 — Lean Monorepo Structure](../adr/0001-lean-monorepo-structure.md)
- Issue: [#9](https://github.com/Redna/evol-hive/issues/9)

## Requirements

### Shared Layer (`@evol-hive/shared`)

1. **`ReflectResult` type** — A new interface `ReflectResult` must be defined in `packages/shared/src/types/cognition.ts` representing the outcome of the Reflect phase: `{ success: boolean; error?: string; cycleComplete: boolean; memoryStored: boolean; goalUpdated: boolean; drivesUpdated: boolean }`. On success, `cycleComplete` is `true` (the PPER cycle is done and ready for the next Perceive). On failure (LLM error, validation error), `cycleComplete` is `false` (the PPER orchestrator should retry on the next tick), `error` contains the failure reason, and `memoryStored`, `goalUpdated`, and `drivesUpdated` are all `false`. On success, `memoryStored` is `true` only if a memory entry was provided by the LLM and successfully stored; `goalUpdated` is `true` only if `newGoal` was provided and applied; `drivesUpdated` is `true` only if `driveOverrides` were provided and applied.

2. **`ReflectLLMResponse` type** — A new interface `ReflectLLMResponse` must be defined in `packages/shared/src/types/cognition.ts` representing the structured output the LLM returns during the Reflect phase: `{ newGoal?: string; driveOverrides?: Partial<Record<string, number>>; memoryEntry?: MemoryEntryInput }`. This extends the existing `UpdateStateResult` (§8.3) with an optional `memoryEntry` field. All three fields are optional — the LLM may choose to update only the goal, only drives, only store a memory, or any combination.

3. **`MemoryEntryInput` type** — A new interface `MemoryEntryInput` must be defined in `packages/shared/src/types/cognition.ts` representing the LLM-generated memory entry to store: `{ content: string; importance: number; type: MemoryType; location?: string }`. The `content` is a natural-language description of what happened and/or what was learned. The `importance` is an integer 1–10 (per §11.2). The `type` is one of the existing `MemoryType` values (`'observation' | 'reflection' | 'action' | 'interaction'`). The optional `location` is the room/scene ID where the event occurred. This type excludes `id`, `agentId`, `embedding`, and `timestamp` — those are generated by the system when the full `MemoryNode` is created.

4. **`reflectSchema` constant** — A new JSON schema constant `reflectSchema` must be defined in `packages/shared/src/schemas/llm-schemas.ts` for use as a grammar constraint / `response_format` with the LLM backend. The schema must enforce the `ReflectLLMResponse` shape:
   ```json
   {
     "type": "object",
     "properties": {
       "newGoal": { "type": ["string", "null"] },
       "driveOverrides": {
         "type": "object",
         "additionalProperties": { "type": "number" }
       },
       "memoryEntry": {
         "type": ["object", "null"],
         "properties": {
           "content": { "type": "string" },
           "importance": { "type": "integer", "minimum": 1, "maximum": 10 },
           "type": { "type": "string", "enum": ["observation", "reflection", "action", "interaction"] },
           "location": { "type": ["string", "null"] }
         },
         "required": ["content", "importance", "type"],
         "additionalProperties": false
       }
     },
     "additionalProperties": false
   }
   ```
   No fields are required at the top level — the LLM may return an empty object `{}` if it decides no updates are needed. This follows the same grammar-constraint pattern as `llmActionResponseSchema` and `formulatePlanSchema` (§7).

5. **`ReflectDataProvider` interface** — A new bridge interface `ReflectDataProvider` must be defined in `packages/shared/src/types/cognition.ts` (per ADR-0001, cognition must not import from engine or memory). It must declare:
   ```typescript
   interface ReflectDataProvider {
     getAgentState(agentId: string): AgentInternalState | null;
     applyDriveChanges(agentId: string, changes: Partial<Record<string, number>>): void;
     updateGoal(agentId: string, goal: string): void;
     storeMemory(agentId: string, entry: MemoryEntryInput): Promise<void>;
     clearPlanIfComplete(agentId: string): boolean;
     setThinking(agentId: string, isThinking: boolean): void;
   }
   ```
   This follows the `ExecuteDataProvider` and `PlanDataProvider` bridge pattern from specs 002 and 003. Some methods overlap with existing providers (e.g., `getAgentState`, `setThinking`) — the same engine class may implement multiple provider interfaces. The `clearPlanIfComplete` method checks if the plan is complete (all steps executed) and, if so, clears it (sets `currentPlan` to `null`), returning `true`. If the plan is not complete, it returns `false` without modifying the plan. This ensures the next Plan phase can formulate a new plan.

### Memory Layer (`@evol-hive/memory`)

6. **`EmbeddingProvider` interface** — A new interface `EmbeddingProvider` must be defined in `packages/memory/src/index.ts`:
   ```typescript
   interface EmbeddingProvider {
     /** Embedding dimensionality (must match the vector store's expected dimension). */
     readonly dimensions: number;
     /** Generate an embedding vector for a single text input. */
     embed(text: string): Promise<number[]>;
   }
   ```
   This is needed because the existing `VectorStore.store(node: MemoryNode)` requires a pre-computed `embedding` field on the `MemoryNode`. The `EmbeddingProvider` generates this embedding from the memory entry's `content` text. The existing `EmbeddingProvider` in `packages/cognition/src/classifier/embedding/index.ts` (used by the System 0 classifier) has the same shape — this new interface in the memory package allows the memory subsystem to have its own embedding model (or share the same one via dependency injection). The memory package must not import from cognition.

7. **`MemoryStore` interface** — A new interface `MemoryStore` must be defined in `packages/memory/src/index.ts` that wraps the `VectorStore` and `EmbeddingProvider` to provide a simplified store API:
   ```typescript
   interface MemoryStore {
     /** Store a memory entry — generates embedding, creates full MemoryNode, persists to VectorStore. */
     store(agentId: string, entry: MemoryEntryInput, timestamp: number): Promise<MemoryNode>;
     /** Retrieve a memory by ID. */
     get(id: string): Promise<MemoryNode | null>;
   }
   ```
   The `store` method: (a) generates an embedding via `EmbeddingProvider.embed(entry.content)`, (b) creates a `MemoryNode` with a generated `id` (e.g., `mem_${agentId}_${timestamp}_${counter}`), the `agentId`, `entry.content`, the embedding, `entry.importance`, `entry.type`, `entry.location` (if provided), and the `timestamp`, (c) calls `VectorStore.store(node)`, and (d) returns the created `MemoryNode`. This abstracts the embedding generation step away from the engine's `ReflectDataProviderImpl`.

8. **`MemoryStoreImpl` concrete implementation** — A concrete `MemoryStoreImpl` class must be implemented in `packages/memory/src/store/index.ts`, exported from `packages/memory/src/index.ts`. It must accept `{ vectorStore: VectorStore; embeddingProvider: EmbeddingProvider }` via constructor injection. The `store` method must generate a unique `id` using a monotonic counter to guarantee uniqueness within the same millisecond (following the `PlanManagerImpl` pattern from spec 002). The `get` method delegates to `VectorStore.get(id)`.

### Cognition Layer (`@evol-hive/cognition`)

9. **`ReflectService` interface** — A new interface `ReflectService` must be defined in `packages/cognition/src/index.ts` with a method `reflect(agentId: string, executeResult: ExecuteResult): Promise<ReflectResult>`. This is the entry point for the Reflect phase, invoked by the PPER orchestrator after the Execute phase completes (whether success or failure). The `executeResult` parameter carries the outcome of the Execute phase — the Reflect phase uses it to inform the LLM about what happened.

10. **`ReflectBuilder` interface** — A new interface `ReflectBuilder` must be defined in `packages/cognition/src/index.ts`:
    ```typescript
    interface ReflectBuilder {
      build(agentId: string, agentState: AgentInternalState, executeResult: ExecuteResult): LLMContextPayload;
    }
    ```
    This builds the LLM context payload for the Reflect phase. Unlike `PerceptionBuilder` and `PlanBuilder` which take `PerceptionResult`, the `ReflectBuilder` takes the agent's current state and the execution result — these are the inputs the LLM needs to reflect on.

11. **`ReflectBuilderImpl` concrete implementation** — A concrete `ReflectBuilderImpl` class must be implemented in `packages/cognition/src/pper/reflect-builder.ts`, exported from `packages/cognition/src/pper/index.ts`. The `build` method must produce an `LLMContextPayload` with:
    - `systemPrompt`: A prompt instructing the LLM to reflect on the action outcome, evaluate whether the agent's goal or drives need adjustment, and decide if a memory entry should be stored. The prompt must mention the `update_internal_state` cognitive tool.
    - `perceptionContext`: A formatted string containing: the execution result (success/failure, error message if any, affordance result summary), the agent's current drives snapshot, the agent's current goal, and the plan status (complete or in-progress with remaining steps).
    - `availableAffordances`: An empty array `[]` (affordances are not relevant during reflection).
    - `cognitiveTools`: An array containing only the `update_internal_state` tool definition (from `defaultCognitiveTools` in `packages/cognition/src/tools/index.ts`).
    - `responseSchema`: The `reflectSchema` constant (Req 4).

12. **`completeReflect` method on `LLMClient`** — A new method `completeReflect(payload: LLMContextPayload): Promise<ReflectLLMResponse>` must be added to the `LLMClient` interface in `packages/cognition/src/index.ts`. This method sends a structured output request to the LLM backend with the `reflectSchema` as the grammar constraint and parses the response into a `ReflectLLMResponse`. This follows the same pattern as `completePlan` (which uses `formulatePlanSchema`) and `completeStructured` (which uses `llmActionResponseSchema`).

13. **`ReflectServiceImpl` — orchestration** — A concrete `ReflectServiceImpl` class must be implemented in `packages/cognition/src/pper/reflect-service.ts`, exported from `packages/cognition/src/pper/index.ts`. It must accept `ReflectServiceOptions` (containing `reflectBuilder: ReflectBuilder`, `llmClient: LLMClient`, `dataProvider: ReflectDataProvider`) via constructor injection. The `reflect(agentId, executeResult)` method must perform the following orchestration:
    - Retrieve the agent's state via `dataProvider.getAgentState(agentId)`. If the agent does not exist, return `ReflectResult { success: false, error: "Agent not found", cycleComplete: false, memoryStored: false, goalUpdated: false, drivesUpdated: false }`.
    - Set `isThinking` to `true` via `dataProvider.setThinking(agentId, true)` before the LLM call (§9.1).
    - Build the context payload via `reflectBuilder.build(agentId, agentState, executeResult)`.
    - Call `llmClient.completeReflect(payload)` and await the `ReflectLLMResponse`.
    - Validate the LLM response (see Req 15). If invalid, return a failure `ReflectResult` (see Req 15).
    - Apply `driveOverrides` if present and non-empty (see Req 16).
    - Apply `newGoal` if present and non-empty (see Req 17).
    - Store `memoryEntry` if present (see Req 18).
    - Clear the plan if it is complete (see Req 19).
    - Return a success `ReflectResult` with `cycleComplete: true` and the appropriate flags set.
    - On any exception, catch it, call `setThinking(agentId, false)`, and return a failure `ReflectResult` (see Req 20).
    - On success, call `setThinking(agentId, false)` in a `finally` block (same pattern as `PlanServiceImpl`).

14. **`ReflectServiceOptions` type** — A new interface `ReflectServiceOptions` must be defined in `packages/cognition/src/pper/reflect-service.ts`:
    ```typescript
    interface ReflectServiceOptions {
      reflectBuilder: ReflectBuilder;
      llmClient: LLMClient;
      dataProvider: ReflectDataProvider;
    }
    ```

15. **LLM response validation** — The `ReflectServiceImpl` must validate the `ReflectLLMResponse` before applying any changes:
    - If `newGoal` is present, it must be a non-empty string. If it is an empty string, it is treated as `undefined` (no goal update).
    - If `driveOverrides` is present, it must be a non-empty object. If it is an empty object `{}`, it is treated as `undefined` (no drive changes).
    - If `memoryEntry` is present, `content` must be a non-empty string, `importance` must be an integer 1–10, and `type` must be one of the valid `MemoryType` values. If any of these checks fail, the entire `ReflectResult` is a failure: `{ success: false, error: "Invalid memory entry from LLM: <reason>", cycleComplete: false, memoryStored: false, goalUpdated: false, drivesUpdated: false }`. No partial updates are applied — if the memory entry is invalid, no drives or goal updates are applied either (atomicity).
    - If the response is `undefined` or `null`, treat it as an empty object `{}` (no updates needed — the LLM decided nothing needs to change). This is a valid success case.

16. **Apply drive overrides** — When `driveOverrides` is present and non-empty, the `ReflectServiceImpl` must call `dataProvider.applyDriveChanges(agentId, driveOverrides)`. The `ReflectDataProvider.applyDriveChanges` method delegates to `DriveSystem.applyChanges`, which clamps values to 0–100 (per existing `DriveSystemImpl`). The `drivesUpdated` flag in the `ReflectResult` must be set to `true`. If `driveOverrides` is absent or empty, `drivesUpdated` is `false`.

17. **Update goal** — When `newGoal` is present and non-empty, the `ReflectServiceImpl` must call `dataProvider.updateGoal(agentId, newGoal)`. The `ReflectDataProvider.updateGoal` method delegates to `AgentManager.updateState(agentId, { currentGoal: newGoal })`. The `goalUpdated` flag in the `ReflectResult` must be set to `true`. If `newGoal` is absent or empty, `goalUpdated` is `false`.

18. **Store memory entry** — When `memoryEntry` is present and valid, the `ReflectServiceImpl` must call `dataProvider.storeMemory(agentId, memoryEntry)` and await the result. The `memoryStored` flag in the `ReflectResult` must be set to `true` if the store succeeds. If the store call throws an exception, the `ReflectServiceImpl` must catch it and return `ReflectResult { success: false, error: "Failed to store memory: <message>", cycleComplete: false, memoryStored: false, goalUpdated: <whether goal was already updated>, drivesUpdated: <whether drives were already updated> }`. If `memoryEntry` is absent, `memoryStored` is `false`.

19. **Clear plan if complete** — After all updates are applied, the `ReflectServiceImpl` must call `dataProvider.clearPlanIfComplete(agentId)`. If the plan is complete (all steps executed), the plan is cleared (set to `null`) so the next Plan phase can formulate a new plan. If the plan is not complete, it is left intact — the next cycle will continue executing remaining steps. This call must not throw — if it fails, it should be logged but not cause the Reflect phase to fail (the plan clearing is a side-effect, not a critical operation). The `cycleComplete` flag in the `ReflectResult` must always be `true` on the success path, regardless of whether the plan was cleared.

20. **Exception handling and `isThinking` safety** — The `reflect(agentId, executeResult)` method must catch any exception thrown by the LLM client or data provider calls and return `ReflectResult { success: false, error: <exception message>, cycleComplete: false, memoryStored: false, goalUpdated: false, drivesUpdated: false }`. It must **not** re-throw. Before returning on any error path, it must call `dataProvider.setThinking(agentId, false)` to guarantee the agent is not frozen (§9.1). On the success path, `setThinking(agentId, false)` must be called in a `finally` block — the same pattern as `PlanServiceImpl` (spec 002, Req 6). This ensures `isThinking` is always `false` after the Reflect phase, whether it succeeded or failed.

21. **No-op on skipped steps** — When `executeResult.stepSkipped` is `true` (the Execute phase skipped a non-physical step, per spec 003 Req 12), the `ReflectServiceImpl` may still call the LLM to reflect on the skip, but it is not required to. The `ReflectBuilder` must include the `stepSkipped` flag in the context so the LLM knows the step was skipped, not executed. The LLM may decide to store a memory entry about the skip (e.g., "Moved to the kitchen") or return an empty response. Both are valid outcomes.

### Engine Layer (`@evol-hive/engine`)

22. **`ReflectDataProviderImpl` bridge** — A concrete `ReflectDataProviderImpl` class must be implemented in `packages/engine/src/agents/index.ts` (or a dedicated file in `packages/engine/src/agents/`). It must implement the `ReflectDataProvider` interface (defined in shared, Req 5) using `AgentManager`, `DriveSystem`, `PlanManager`, and `MemoryStore`:
    - `getAgentState(agentId)` → delegates to `AgentManager.getState(agentId)`.
    - `applyDriveChanges(agentId, changes)` → delegates to `DriveSystem.applyChanges(agentId, changes)`.
    - `updateGoal(agentId, goal)` → delegates to `AgentManager.updateState(agentId, { currentGoal: goal })`.
    - `storeMemory(agentId, entry)` → delegates to `MemoryStore.store(agentId, entry, <current simulation time>)`. The simulation time is provided via a `SimulationClock` function injected at construction time (same pattern as `PlanManagerImpl`).
    - `clearPlanIfComplete(agentId)` → checks `PlanManager.isComplete(agentId)`. If `true`, calls `PlanManager.clearPlan(agentId)` and returns `true`. If `false`, returns `false` without modifying the plan.
    - `setThinking(agentId, isThinking)` → delegates to `AgentManager.updateState(agentId, { isThinking })`.

23. **`ReflectDataProviderImpl` constructor** — The `ReflectDataProviderImpl` must accept the following via constructor injection:
    ```typescript
    constructor(
      agentManager: AgentManager,
      driveSystem: DriveSystem,
      planManager: PlanManager,
      memoryStore: MemoryStore,
      clock: SimulationClock,
    )
    ```
    The `MemoryStore` is injected from the `@evol-hive/memory` package. Per ADR-0001, the engine package may depend on the memory package (the dependency graph is: `shared ← engine`, `shared ← memory`, `memory ← cognition`). The engine-to-memory dependency is acceptable because the engine writes memories during the Reflect phase. The `SimulationClock` is the same `() => number` type used by `PlanManagerImpl`.

### Cross-Cutting

24. **LLM call is required** — Unlike the Execute phase (which is deterministic), the Reflect phase is System 2 (LLM-driven, §6). It must call `llmClient.completeReflect()` on every invocation. However, if the LLM returns an empty response `{}`, no state changes are applied — this is a valid "no reflection needed" outcome.

25. **Package boundaries** (per ADR-0001) — `cognition` and `engine` must **not** directly import from each other. All cross-package communication must go through interfaces defined in `@evol-hive/shared`. The `ReflectDataProvider` bridge (defined in `shared`) is the only communication channel between cognition and engine. The `cognition` package imports from `@evol-hive/shared` and `@evol-hive/memory` (for the `MemoryEntryInput` type only — it does not import from `@evol-hive/memory` implementations). The `engine` package imports from `@evol-hive/shared` and `@evol-hive/memory` (for `MemoryStore` and `MemoryStoreImpl`). The `memory` package imports from `@evol-hive/shared` only.

26. **Atomicity of state updates** — Drive overrides, goal updates, and memory storage are applied in sequence: (1) drives, (2) goal, (3) memory. If the memory store call fails, the drives and goal updates that were already applied are **not** rolled back — the `ReflectResult` reports which updates were applied via the `drivesUpdated` and `goalUpdated` flags. This is a deliberate trade-off: rollback would require transactional semantics that add complexity without clear benefit at this stage. The PPER orchestrator can retry the full Reflect phase on the next tick if needed.

27. **`isThinking` safety** — The `isThinking` flag must be set to `true` before the LLM call and reset to `false` on every exit path (success, failure, exception). Leaving `isThinking = true` permanently freezes the agent in the game loop (§9.1). Use the same `try/catch/finally` pattern as `PlanServiceImpl` (spec 002): `setThinking(true)` before the try block, `setThinking(false)` in the `finally` block, and `setThinking(false)` before returning on early-exit paths (agent not found).

28. **No plan modification beyond clearing** — The Reflect phase must not create new plans, modify plan descriptions, or add/remove steps. It may only clear the plan (set `currentPlan` to `null`) when the plan is complete. Re-planning is the responsibility of the next Plan phase. Modifying `AgentPlan.description`, `steps`, or `currentStepIndex` during Reflect is a hard violation.

29. **Drive clamping** — Drive overrides from the LLM must be applied via `DriveSystem.applyChanges`, which clamps to 0–100. Directly modifying `AgentInternalState.drives` without clamping is a violation. This prevents overflow/underflow in drive values. The LLM may suggest drive changes of any magnitude (e.g., `+50` or `-30`), but the final value is always clamped.

30. **Memory storage is best-effort** — If the `MemoryStore` or `EmbeddingProvider` is not wired (e.g., in a test environment without a vector store), the `storeMemory` call may throw. The `ReflectServiceImpl` must catch this and report it in the `ReflectResult` without crashing the PPER cycle. The cycle still completes (`cycleComplete: true` on the success path) even if memory storage fails — memory is an enhancement, not a critical-path operation. However, if memory storage fails, `memoryStored` is `false` and `success` is `false` (the Reflect phase partially failed).

31. **Reuse from specs 001, 002, and 003** — The `AgentInternalState`, `AgentDrives`, `AgentPlan`, `ExecuteResult`, `AffordanceResult`, `MemoryNode`, `MemoryType`, `MemorySnippet`, `LLMContextPayload`, `LLMClient`, `CognitiveTool`, `defaultCognitiveTools`, `AgentManager`, `DriveSystem`, `PlanManager`, `SimulationClock`, `VectorStore`, `PerceptionDataProvider`, `PlanDataProvider`, and `ExecuteDataProvider` types/interfaces are already defined. This spec adds `ReflectResult`, `ReflectLLMResponse`, `MemoryEntryInput`, `reflectSchema`, `ReflectDataProvider`, `ReflectService`, `ReflectBuilder`, `ReflectBuilderImpl`, `ReflectServiceImpl`, `EmbeddingProvider`, `MemoryStore`, `MemoryStoreImpl`, `ReflectDataProviderImpl`, and the `completeReflect` method on `LLMClient` — it does not redefine existing types.

32. **What NOT to do**:
    - Do not implement the PPER orchestrator's phase-transition state machine — that is a separate spec.
    - Do not implement the background reflection/consolidation loop (§11.3) — that is a separate concern from the real-time Reflect phase. The background loop consolidates existing memories asynchronously; the Reflect phase stores new memories synchronously as part of the PPER cycle.
    - Do not implement the `query_memory` cognitive tool (active recall, §11.1 Track 2) — that is a separate spec.
    - Do not implement the `formulate_plan` cognitive tool execution — that is already handled by the Plan phase (spec 002).
    - Do not implement LLM client backends (Ollama, vLLM, llama.cpp) — the `completeReflect` method is an interface addition; the backend implementation is deferred.
    - Do not implement the game loop, async routing infrastructure, or `LLMConcurrencyManager` (§9).
    - Do not implement cognitive guardrails (§10) — the Reflect phase does not use guardrails.
    - Do not implement the full memory retrieval subsystem (weighted retrieval scoring, associative memory injection) — only the storage path is in scope.
    - Do not add `ReflectResult`, `ReflectLLMResponse`, `MemoryEntryInput`, or `ReflectDataProvider` to `packages/engine/` or `packages/cognition/` — they belong in `shared` since multiple packages need to reference them.

## Constraints

- **Package boundaries** (per ADR-0001): `cognition` and `engine` must **not** directly import from each other. All cross-package communication must go through interfaces defined in `@evol-hive/shared`. The `ReflectDataProvider` bridge (defined in `shared`) is the only communication channel. The `engine` package may depend on `@evol-hive/memory` for `MemoryStore` (the dependency graph allows `engine → memory`). The `cognition` package may reference `MemoryEntryInput` from `@evol-hive/shared` but must not import from `@evol-hive/memory` implementations.
- **LLM call is required**: The Reflect phase is System 2 (LLM-driven). It must call `llmClient.completeReflect()` on every invocation. Unlike the Execute phase, there is no "skip the LLM" fast path. However, the LLM may return an empty response `{}` indicating no updates are needed.
- **`isThinking` safety**: The `isThinking` flag must be set to `true` before the LLM call and `false` on every exit path. Use the `try/catch/finally` pattern from `PlanServiceImpl` (spec 002): `setThinking(true)` before the try block, `setThinking(false)` in the `finally` block. For the early-exit path (agent not found), call `setThinking(false)` before returning. Leaving `isThinking = true` permanently freezes the agent (§9.1).
- **Atomicity of validation**: If the LLM's `memoryEntry` is invalid (empty content, importance out of range, invalid type), the entire Reflect result is a failure — no partial updates (drives, goal) are applied. This prevents inconsistent state where drives were updated but the memory entry that motivated the update was rejected.
- **Non-atomicity of application**: Once validation passes, updates are applied in sequence (drives → goal → memory). If the memory store call fails after drives and goal were applied, those updates are not rolled back. The `ReflectResult` flags report which updates succeeded. This is a deliberate trade-off — rollback adds complexity without clear benefit at this stage.
- **No plan modification**: The Reflect phase must not create, modify, or advance plans. It may only clear the plan when it is complete. Re-planning is the next Plan phase's responsibility.
- **Drive clamping**: Drive overrides must be applied via `DriveSystem.applyChanges`, which clamps to 0–100. Directly modifying `AgentInternalState.drives` is a violation.
- **Memory storage is best-effort**: If the `MemoryStore` or `EmbeddingProvider` is not wired, the `storeMemory` call may throw. The `ReflectServiceImpl` must catch this and report it without crashing the PPER cycle. However, the `success` flag is `false` in this case — the Reflect phase partially failed.
- **Interface-first pattern**: Follow the existing pattern — define interfaces in `shared` or `cognition`, implement in the appropriate package. `ReflectDataProvider` goes in `shared`; `ReflectService` and `ReflectBuilder` go in `cognition`; `ReflectDataProviderImpl` goes in `engine`; `MemoryStore` and `EmbeddingProvider` go in `memory`; `ReflectBuilderImpl` and `ReflectServiceImpl` go in `cognition`.
- **Reuse from specs 001, 002, and 003**: All existing types (`AgentInternalState`, `AgentDrives`, `AgentPlan`, `ExecuteResult`, `AffordanceResult`, `MemoryNode`, `MemoryType`, `LLMContextPayload`, `LLMClient`, `CognitiveTool`, `defaultCognitiveTools`, `AgentManager`, `DriveSystem`, `PlanManager`, `SimulationClock`, `VectorStore`) are already defined. This spec only adds new types and interfaces — it does not redefine or modify existing ones (except adding `completeReflect` to the `LLMClient` interface).
- **Schema naming**: The schema is named `reflectSchema` (not `updateStateSchema` as shorthand in the issue). This follows the naming convention of `llmActionResponseSchema`, `formulatePlanSchema`, and `updateInternalStateSchema`. The schema extends the `updateInternalStateSchema` pattern with an additional `memoryEntry` field.
- **What NOT to do**:
  - Do not implement the PPER orchestrator's phase-transition state machine.
  - Do not implement the background reflection/consolidation loop (§11.3) — that is asynchronous and separate from the real-time Reflect phase.
  - Do not implement the `query_memory` cognitive tool (active recall, §11.1 Track 2).
  - Do not implement LLM client backends (Ollama, vLLM, llama.cpp).
  - Do not implement the game loop, async routing infrastructure, or `LLMConcurrencyManager` (§9).
  - Do not implement cognitive guardrails (§10).
  - Do not implement the full memory retrieval subsystem (weighted retrieval scoring, associative memory injection).
  - Do not add `ReflectResult`, `ReflectLLMResponse`, `MemoryEntryInput`, or `ReflectDataProvider` to `packages/engine/` or `packages/cognition/` — they belong in `shared`.
