# Feature: Object Interactions — Multi-Step Affordances, Object State Changes, Dependencies

## Context
- Architecture: [§4 — Smart Objects & Affordances](../architecture/04-smart-objects.md) (SmartObject, Affordance, preconditions, engineEffect), [§5 — Fast-Path Classifier](../architecture/05-fast-path-classifier.md) (affordance pruning), [§6 — PPER Loop](../architecture/06-pper-loop.md) (perceive → plan → execute → reflect), [§9 — Engine Routing](../architecture/09-engine-routing.md) (action feedback loop)
- Related specs: [003 — Execute Phase](003-execute-phase.md) (affordance execution, precondition checking, state updates), [013 — Richer Scenes](013-richer-prototype-scenes.md) (multi-object scenes, state depletion, precondition checkers), [002 — Plan Phase](002-plan-phase.md) (plan formulation, FormulatePlanResult), [001 — Perceive Phase](001-perceive-phase.md) (PerceptionResult, prunedAffordances)
- Package: `shared` (type extensions), `engine` (object state evolution, conditional affordance evaluation, tick system, dependency graph), `cognition` (dependency-aware plan building, conditional affordance pruning)
- ADR: [ADR-0001 — Lean Monorepo Structure](../adr/0001-lean-monrope-structure.md)
- Issue: [#63](https://github.com/Redna/evol-hive/issues/63)

## Design Rationale

The current system supports simple affordances (e.g., `brew_coffee` gives +20 energy) with string-keyed precondition checkers and state updates via `AffordanceResult.newState`. However, objects lack autonomous state evolution, multi-step affordance sequences, inter-object dependencies, and conditional affordance availability based on runtime state.

This spec extends the existing architecture incrementally:

1. **Object state evolution** is implemented as a new tick-driven `EngineSystem` (`ObjectStateSystem`) that runs per-tick state mutations on registered objects. This mirrors the existing `DriveDecaySystem` pattern — a system registered with the game loop that calls `update(tick)` every frame.

2. **Multi-step affordances** are modelled declaratively via a new `steps` field on `Affordance`. Each step is itself an affordance ID with its own preconditions. The `Affordance` type already has `preconditions: string[]` — steps extend this by requiring that the agent plan a sequence of sub-affordances. The LLM already uses `formulate_plan` to create multi-step plans; this spec makes the steps explicit in the affordance definition so the plan builder can surface them.

3. **Object dependencies** are modelled as a directed graph on `SmartObject`: an affordance can declare `requiresObjects: { objectId: string; roomHint?: string }[]`. The plan builder receives dependency metadata in the `LLMContextPayload` so the LLM can plan navigation + interaction sequences. Dependencies are not enforced at execution time (the agent can still attempt an action) — they are advisory for the plan phase, keeping the execute phase deterministic and simple.

4. **Conditional affordances** extend the existing precondition system with a new `ConditionChecker` registry on the engine side. The classifier's `getAffordancesInRoom` output is filtered by the engine before pruning: affordances whose conditions evaluate to `false` are excluded. This prevents the LLM from seeing affordances that are currently unavailable.

5. **Object replenishment** is a natural consequence of affordance handlers that mutate object state (e.g., `refill_water` sets `water_level` to `max`). No new infrastructure is needed beyond what the existing `AffordanceHandler` + `SmartObjectRegistry.updateState` already provides — this spec defines the patterns and helper types.

The design avoids changes to the PPER orchestrator, the game loop infrastructure, or the `ExecuteServiceImpl` flow. All extensions are additive: new types, new registries, a new engine system, and enhanced context payloads.

## Requirements

### Shared Layer (`@evol-hive/shared`)

1. **`AffordanceStep` type** — Define a new interface `AffordanceStep` in `packages/shared/src/types/affordance.ts` representing a single step in a multi-step affordance: `{ affordanceId: string; label: string; preconditions: string[] }`. The `affordanceId` is the semantic name of the sub-affordance (e.g., `"add_water"`). The `label` is a human/LLM-readable description. The `preconditions` are the precondition names that must pass before this step can execute.

2. **`steps` field on `Affordance`** — Add an optional field `steps?: AffordanceStep[]` to the `Affordance` interface in `packages/shared/src/types/affordance.ts`. When present, the affordance is a composite action requiring the agent to plan and execute each sub-step in order. When absent, the affordance is atomic (current behavior). The `steps` array defines the canonical order of sub-steps.

3. **`ObjectDependency` type** — Define a new interface `ObjectDependency` in `packages/shared/src/types/affordance.ts`: `{ objectId: string; label: string; roomHint?: string }`. The `objectId` references a `SmartObject.id`. The `label` is a human-readable description of why the dependency exists (e.g., `"Provides water for refilling"`). The `roomHint` is the room ID where the dependency object is located, if known.

4. **`requiresObjects` field on `Affordance`** — Add an optional field `requiresObjects?: ObjectDependency[]` to the `Affordance` interface. When present, the affordance depends on the referenced objects being available (typically in a different room). This is advisory metadata for the plan builder — it is NOT enforced at execution time.

5. **`ObjectStateMutation` type** — Define a new interface `ObjectStateMutation` in `packages/shared/src/types/affordance.ts`: `{ field: string; operation: 'set' | 'increment' | 'decrement' | 'multiply'; value: number }`. This describes a deterministic state mutation applied to a `SmartObject.state` field. `set` replaces the field value. `increment` adds the value. `decrement` subtracts the value. `multiply` multiplies the field by the value.

6. **`StateEvolutionRule` type** — Define a new interface `StateEvolutionRule` in `packages/shared/src/types/affordance.ts`: `{ field: string; operation: 'set' | 'increment' | 'decrement' | 'multiply'; value: number; intervalSeconds: number }`. This describes an autonomous state change applied on a time interval. The `intervalSeconds` determines how often the mutation fires. For example, `{ field: "temperature", operation: "decrement", value: 1, intervalSeconds: 60 }` means the coffee machine's temperature drops by 1 every 60 seconds.

7. **`stateEvolution` field on `SmartObject`** — Add an optional field `stateEvolution?: StateEvolutionRule[]` to the `SmartObject` interface in `packages/shared/src/types/affordance.ts`. When present, the `ObjectStateSystem` applies these rules on each tick based on the elapsed simulation time.

8. **`ConditionChecker` type** — Define a new type `ConditionChecker` in `packages/shared/src/types/affordance.ts`: `(objectState: Record<string, unknown>) => boolean`. This is identical in signature to `PreconditionChecker` but is used for availability filtering (affordance pruning) rather than execution gating. A condition checker returning `false` means the affordance is currently unavailable and should be hidden from the LLM.

9. **`conditions` field on `Affordance`** — Add an optional field `conditions?: string[]` to the `Affordance` interface. Each string is a condition checker name (e.g., `"water_not_full"`). When present, the engine evaluates all listed condition checkers against the owning object's state before including the affordance in `getAffordancesInRoom`. If any condition checker returns `false`, the affordance is excluded. When absent, the affordance is always included (subject to precondition checks at execution time). This is distinct from `preconditions`: conditions filter visibility (System 0 / classifier), preconditions gate execution (Execute phase).

10. **`DependencyInfo` type for plan context** — Define a new interface `DependencyInfo` in `packages/shared/src/types/cognition.ts`: `{ affordanceId: string; dependencies: { objectId: string; objectName: string; roomId: string; label: string }[] }`. This is the resolved dependency metadata passed to the plan builder so the LLM can reason about where to navigate before executing an affordance.

11. **`getConditionalAffordancesInRoom` on `PerceptionDataProvider`** — Add a new optional method to the `PerceptionDataProvider` interface in `packages/shared/src/types/cognition.ts`: `getConditionalAffordancesInRoom?(roomId: string): Affordance[]`. This returns all affordances in a room after filtering out those whose `conditions` evaluate to `false`. When this method is present, the perception service must call it instead of `getAffordancesInRoom`. When absent, the perception service falls back to `getAffordancesInRoom` (backward compatibility).

12. **`getDependencyInfo` on `PerceptionDataProvider`** — Add a new optional method to the `PerceptionDataProvider` interface: `getDependencyInfo?(roomId: string): DependencyInfo[]`. This resolves `requiresObjects` on all affordances in a room to concrete `{ objectId, objectName, roomId, label }` tuples by looking up each `ObjectDependency.objectId` in the `SmartObjectRegistry`. Returns an empty array when no affordances in the room have dependencies.

### Engine Layer (`@evol-hive/engine`)

13. **`ConditionCheckerRegistry`** — Define a new interface `ConditionCheckerRegistry` in `packages/engine/src/world/affordances/index.ts` with methods `registerConditionChecker(name: string, checker: ConditionChecker): void` and `getConditionChecker(name: string): ConditionChecker | null`. The `AffordanceRegistryImpl` class must be extended to implement this interface (adding a `conditionCheckers` map alongside the existing `preconditionCheckers` map). Condition checkers are registered at engine initialization time, following the same pattern as precondition checkers.

14. **`evaluateConditions` method on `AffordanceRegistryImpl`** — Add a method `evaluateConditions(affordance: Affordance, objectId: string): boolean` to `AffordanceRegistryImpl`. This looks up the `SmartObject` by `objectId`, iterates the affordance's `conditions` array (if present), and invokes each registered `ConditionChecker` with the object's `state`. Returns `true` if all conditions pass (or if `conditions` is absent/empty). Returns `false` if any condition checker returns `false` or is not registered (fail-safe, same as preconditions).

15. **Conditional affordance filtering in `SmartObjectRegistryImpl`** — Add a method `getConditionalAffordancesInRoom(roomId: string, conditionChecker: (affordance: Affordance, objectId: string) => boolean): Affordance[]` to `SmartObjectRegistryImpl`. This iterates all objects in the room, collects all affordances, and filters out those for which `conditionChecker` returns `false`. The `ExecuteDataProviderImpl` (or a new `PerceptionDataProviderImpl` enhancement) calls this with `affordanceRegistry.evaluateConditions.bind(affordanceRegistry)` to produce the conditionally-filtered affordance list.

16. **`ObjectStateSystem` — tick-driven state evolution** — Implement a new `EngineSystem` in `packages/engine/src/systems/object-state.ts` named `ObjectStateSystem`. It maintains a `Map<string, { rule: StateEvolutionRule; lastFired: number }>` per object (keyed by `objectId + field`). On each `update(tick: GameTick)`, it iterates all registered smart objects that have `stateEvolution` rules. For each rule, if `tick.simulationTime - lastFired >= rule.intervalSeconds`, it applies the `ObjectStateMutation` (field, operation, value) to the object's state via `SmartObjectRegistry.updateState`, and updates `lastFired` to `tick.simulationTime`. The system must be registered with the game loop during engine assembly (in `assembly.ts`), following the same pattern as `DriveDecaySystem`.

17. **`ObjectStateSystem` — registration** — The `ObjectStateSystem` constructor accepts `SmartObjectRegistry`. It discovers objects with `stateEvolution` rules by iterating all registered objects on each `update` call (or caching the list and refreshing on registry changes). Objects without `stateEvolution` are skipped.

18. **`applyStateMutation` helper** — Implement a standalone function `applyStateMutation(state: Record<string, unknown>, mutation: ObjectStateMutation): Record<string, unknown>` in `packages/engine/src/world/affordances/index.ts` (or a new `packages/engine/src/world/state/index.ts`). This applies a single `ObjectStateMutation` to a state object and returns the new state. For `set`, the field is set to `value`. For `increment`, the current value (coerced to `number`, default 0) is incremented by `value`. For `decrement`, decremented by `value`. For `multiply`, multiplied by `value`. The returned state is a shallow copy of the input with the mutated field replaced.

19. **`ExecuteDataProviderImpl` — `getConditionalAffordancesInRoom`** — The `ExecuteDataProviderImpl` (or `PerceptionDataProviderImpl` if it exists separately) must implement `getConditionalAffordancesInRoom(roomId: string): Affordance[]` by delegating to `SmartObjectRegistryImpl.getConditionalAffordancesInRoom` with `affordanceRegistry.evaluateConditions` as the filter callback.

20. **`ExecuteDataProviderImpl` — `getDependencyInfo`** — The data provider must implement `getDependencyInfo(roomId: string): DependencyInfo[]` by iterating all objects in the room, collecting affordances with `requiresObjects`, and for each dependency, looking up the referenced `SmartObject` via `SmartObjectRegistry.get(objectId)` to resolve `objectName` and `roomId`. If the referenced object does not exist, the dependency is omitted (not an error).

21. **Engine assembly — register `ObjectStateSystem`** — The `assembleEngine` function in `packages/engine/src/assembly.ts` must instantiate and register `ObjectStateSystem` with the game loop, after `SmartObjectRegistry` is populated. The system must be registered before the game loop starts (same pattern as `DriveDecaySystem`).

### Cognition Layer (`@evol-hive/cognition`)

22. **Perception service uses conditional affordances** — The `PerceptionServiceImpl` (or the perception builder flow) must call `dataProvider.getConditionalAffordancesInRoom(roomId)` when the method is present on the data provider. The returned (condition-filtered) affordance list is passed to the classifier for pruning instead of the raw `getAffordancesInRoom` list. When `getConditionalAffordancesInRoom` is not present, fall back to `getAffordancesInRoom` (backward compatibility with existing providers).

23. **Plan builder receives dependency metadata** — The `PlanBuilderImpl.build()` method must include dependency information in the `LLMContextPayload.perceptionContext` when `getDependencyInfo` is available and returns non-empty results. The format is: `"Dependencies: <affordanceId> requires <objectName> in <roomId> (<label>); ..."`. When no dependencies exist, no line is added. The plan builder must also include multi-step affordance information in the context: for each pruned affordance with `steps`, include a line: `"<affordanceId> steps: <step1Id>, <step2Id>, ..."`.

24. **Classifier handles composite affordances** — The `AffordanceClassifierImpl.prune()` method must treat composite affordances (those with `steps`) the same as atomic affordances for scoring purposes — the affordance's `label` is embedded and scored against the drive label. The classifier does NOT decompose composite affordances into their sub-steps for pruning. The sub-steps are surfaced to the LLM via the plan builder context (Req 23).

### Cross-Cutting

25. **Backward compatibility** — All new fields on `Affordance` (`steps`, `requiresObjects`, `conditions`) and `SmartObject` (`stateEvolution`) are optional. Existing scene definitions, affordance definitions, object definitions, handlers, precondition checkers, and tests must compile and pass without modification. The `PerceptionDataProvider` methods added in Req 11 and 12 are optional (marked with `?`) so existing implementations remain valid.

26. **Package boundaries** (per ADR-0001) — `cognition` and `engine` must not directly import from each other. All new types (`AffordanceStep`, `ObjectDependency`, `ObjectStateMutation`, `StateEvolutionRule`, `ConditionChecker`, `DependencyInfo`) are defined in `@evol-hive/shared`. The `ConditionCheckerRegistry` and `ObjectStateSystem` live in `@evol-hive/engine`. The perception service and plan builder changes live in `@evol-hive/cognition`. The `PerceptionDataProvider` extensions (Req 11, 12) are bridge interfaces in `@evol-hive/shared`.

27. **Deterministic state evolution** — The `ObjectStateSystem` must be deterministic. Given the same `GameTick.simulationTime` and the same object states, applying state evolution rules must produce the same results. No `Date.now()`, no `Math.random()`, no external I/O. The `lastFired` timestamp is initialized to the simulation time when the system first observes the object (on the first `update` call for that object).

28. **Multi-step execution reuses existing execute flow** — Multi-step affordances do NOT require changes to `ExecuteServiceImpl`. The LLM formulates a plan with one `PlanStep` per sub-step (each `PlanStep.targetAffordance` maps to a sub-affordance ID). The existing execute flow resolves, checks preconditions, executes, and advances per step. The `steps` field on `Affordance` is metadata for the plan builder — it tells the LLM which sub-steps to plan. The sub-steps themselves are registered as independent affordances on the same or different objects.

29. **Replenishment pattern** — Object replenishment is implemented as regular affordance handlers that set object state fields. For example, a `refill_water` affordance handler returns `{ success: true, newState: { ...currentState, water_level: maxWater } }`. No special infrastructure is needed — the existing `AffordanceHandler` + `PhysicsSystemImpl.executeAffordance` + `SmartObjectRegistry.updateState` flow handles this. This spec defines the pattern but does not add new types for it.

## Constraints

- **Package boundaries** (per ADR-0001): `cognition` and `engine` must not directly import from each other. All new types are defined in `@evol-hive/shared`. The `ConditionCheckerRegistry`, `ObjectStateSystem`, and `applyStateMutation` live in `@evol-hive/engine`. The perception service and plan builder changes live in `@evol-hive/cognition`. New `PerceptionDataProvider` methods are bridge interfaces in `@evol-hive/shared`.
- **Backward compatibility**: All new fields on `Affordance` and `SmartObject` are optional. New `PerceptionDataProvider` methods are optional (marked with `?`). Existing scenes, tests, and implementations must compile and pass without modification. This is critical — the spec is additive.
- **Deterministic state evolution**: The `ObjectStateSystem` must be deterministic. `lastFired` is initialized to 0 (or the first tick's `simulationTime`) and tracked against `tick.simulationTime`. No `Date.now()`, `Math.random()`, or external I/O. The same simulation timeline must always produce the same object states.
- **Multi-step execution reuses existing flow**: The `ExecuteServiceImpl` is NOT modified. Multi-step affordances are decomposed into individual `PlanStep` entries by the LLM during plan formulation. Each sub-step is an independent affordance with its own handler, preconditions, and effects. The `steps` field on `Affordance` is advisory metadata for the plan builder — it tells the LLM which sub-steps to plan, not how to execute them.
- **Dependencies are advisory, not enforced**: The `requiresObjects` field is metadata for the plan builder. The execute phase does NOT check whether dependency objects exist before executing an affordance. Dependencies help the LLM plan navigation sequences (e.g., "go to sink, refill water, go to coffee machine, brew"). Enforcing dependencies at execution time would add complexity and break the deterministic, stateless execution model.
- **Conditions filter visibility, preconditions gate execution**: `conditions` (new) determine whether an affordance appears in the pruned list sent to the LLM (System 0). `preconditions` (existing) determine whether the affordance can be executed (Execute phase). An affordance may have both: `conditions` hides it from the LLM when unavailable, `preconditions` reject execution when state is wrong. This separation prevents the LLM from wasting tokens planning around unavailable affordances.
- **No PPER orchestrator changes**: This spec does not modify the PPER orchestrator, the game loop, the PPER scheduler, or the `ExecuteServiceImpl`. All extensions are in the perception service (conditional affordances), plan builder (dependency + steps context), engine systems (object state evolution), and shared types.
- **No new npm dependencies**: This spec uses only existing dependencies. No new embedding models, no new ONNX models, no external libraries.
- **Replenishment is a pattern, not infrastructure**: Object replenishment (e.g., `refill_water` restoring `water_level`) is implemented as regular affordance handlers that return `newState`. No new types, registries, or systems are needed for replenishment. The existing `AffordanceHandler` + `PhysicsSystemImpl` + `SmartObjectRegistry.updateState` flow handles it.
- **Condition checker registration timing**: Condition checkers must be registered at engine initialization time (during world setup), following the same pattern as precondition checkers. The `AffordanceRegistryImpl` must not lazy-register condition checkers. If a condition name has no registered checker, the affordance is treated as unavailable (fail-safe, consistent with precondition handling).
- **State evolution is per-object, not per-affordance**: `StateEvolutionRule` lives on `SmartObject.stateEvolution`, not on `Affordance`. This is because state evolution is a property of the object (e.g., a coffee machine cooling down), not of a specific action. Multiple affordances on the same object share the same evolving state.
- **What NOT to do**:
  - Do not modify `ExecuteServiceImpl` — multi-step affordances use the existing per-step execution flow.
  - Do not modify the PPER orchestrator or game loop infrastructure.
  - Do not enforce object dependencies at execution time — they are advisory for the plan builder only.
  - Do not decompose composite affordances into sub-steps during classifier pruning — the classifier scores the composite affordance as a unit.
  - Do not add `Date.now()` or `Math.random()` to `ObjectStateSystem` — it must be deterministic.
  - Do not create a new perception phase — conditional affordance filtering is an enhancement to the existing perception flow.
  - Do not add new packages — all changes are within `shared`, `engine`, and `cognition`.
  - Do not modify existing `AffordanceHandler` signatures or `PhysicsSystemImpl` execution logic.
  - Do not implement agent-to-agent interactions or social dynamics — this spec is about object interactions only.
  - Do not implement scene transitions or cross-scene object references in dependencies.
