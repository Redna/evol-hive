## Problem Summary

At `ENGINE_MAX_CONCURRENT_LLM=3`, every run ends with all agents' drives pinned at **0** (e/h/s/co/cu = 0 across the last 4 runs). Root cause: the PPER scheduler spreads cycles across 3 agents, so each agent's **effective cycle interval** stretches to 60–90s of sim time, while ambient decay accrues at 0.1/s of **wall sim-time** regardless. Per own-cycle interval an agent loses 6–9 drive points, but its best restoration affordance yields +5 (`relax`) — the economy is structurally net-negative at cc=3 even though it equilibrates at cc=1 (spec 032 AC-5 / 034 Req 9).

Secondary failure: the hunger chain (plant_seeds ×3 → harvest at `seeds_planted >= 3` → eat, +25 hunger) stalled at 2/3 seeds in two runs. Agents narrate hunger but never plant the third time — the spec-034 matcher only surfaces affordances whose declared `effects` positively restore the urgent drive, and `plant_seeds` (+12 curiosity, +4 comfort) declares **no hunger effect**, so the mid-chain step is invisible to the hint system exactly when hunger is critical.

Per-interval ledger at cc=3 (no scaling): decay 6–9/interval vs `relax` +5 energy, `sit_outside` +3/+15 — net-negative on every drive.

## Requirements

### Req 1 — Per-agent decay scaling by active agent count
The `DriveDecaySystem` (`packages/engine/src/systems/drive-decay.ts`) must apply decay to each agent at an **effective rate** of `configuredDecayRate / N`, where `N = agentManager.getActiveAgents().length` at that tick. Decay pressure becomes a scene-level constant (constant total decay per wall sim-minute across the population) instead of a per-agent constant, so per-agent decay is a function of the agent's own cycle cadence, not wall sim-time. At `N = 1` the effective rate equals the configured rate — behavior at cc=1 is byte-identical to today (spec 019 contract intact). Scaling must be configurable via an `EngineConfig` field surfaced from `ENGINE_DECAY_SCALING` (`'per-agent' | 'none'`, default `'per-agent'`), plumbed through `createEngineCore`/`assembly.ts` the same way `maxConcurrentCycles` is.

### Req 2 — Restoration-magnitude audit (economy table, not blind bumps)
A deterministic test must encode the drive-economy ledger for the dynamic-world scene: for **every drive**, the largest restoring affordance `effects` delta available in the scene must exceed the maximum per-interval decay at cc=3 (`decayRate / 3 × mean cycle interval`, mean interval = `SCENE_DURATION_MS / (expected cycles per agent)`). Where the audit fails, restoration magnitudes are raised in `examples/dynamic-world.ts` only for the failing (affordance, drive) pairs. With Req 1's scaling, per-interval decay drops to ~2–3, so the existing +3/+5/+15/+25 magnitudes are expected to pass — the audit formalizes this instead of hand-tuning, protecting equilibrium (AC-3). The sim header's drive-economy table (spec 032 Req 4 / 034 Req 7 pattern) must be updated with the cc=3 numbers.

### Req 3 — Hunger-chain surfacing via declared chain progress (spec 034 matcher extension)
Extend the additive `Affordance` type with an optional `progresses?: { drive: string; note?: string }` field (declared per-affordance in the scene — **no hardcoded drive→chain table in cognition**, preserving spec 034 Req 3's data-driven rule). The matcher (`drive-affordance-matcher.ts`) additionally collects, for each urgent drive, affordances in perception whose `progresses.drive` matches — the **next chain step** toward eventual restoration. The perception and plan hint renderers emit a secondary chain-progress hint line after the direct-restoration hints, e.g.:
`Your hunger is low (23). plant_seeds progresses the hunger chain (harvest → eat restores hunger).`
In `examples/dynamic-world.ts`, `plant_seeds` and `harvest` declare `progresses: { drive: 'hunger' }` (harvest is also a mid-chain step: `eat` — the actual restoration — is gated on `vegetables >= 1`). Chain hints never suppress direct-restoration hints and never apply to the `social` drive (spec 018/024/047 own it).

### Req 4 — Equilibrium preserved (the #139 oscillation)
The rebalance must not turn the drive economy into a monotone maxing slide. At cc=1 the economy is unchanged (Req 1 is a no-op); at cc=3 the audit (Req 2) keeps restoration deltas just above per-interval decay rather than an order of magnitude above. Spec 032 AC-5 / 034 Req 9's oscillation semantics remain the reference behavior.

### Req 5 — Live-run validation protocol at cc=3
A 30-min real-LLM run at `ENGINE_MAX_CONCURRENT_LLM=3` (`USE_REAL_LLM=true SCENE_DURATION_MS=1800000 npx tsx examples/dynamic-world-sim.ts`) is the acceptance instrument for the issue's targets: no drive at 0 at run end, harvest→eat completing in ≥2 of 3 runs, and visible oscillation. Drive traces (`logState()` 15s samples, spec 034 Req 8) are attached to the issue as evidence.

## Acceptance Criteria
- [ ] **AC-1**: A live 30-min run at cc=3 ends with **no agent drive at 0** (all of e/h/s/co/cu > 0 for every agent in the final `logState()` sample). Evidence (drive traces) attached to issue #168. *(maps to Req 1, Req 5 — issue AC-1)*
- [ ] **AC-2**: Across 3 live 30-min cc=3 runs, the hunger chain completes (an `eat` execution with `driveChanges.hunger >= +25`) in **≥ 2 of 3 runs**. *(maps to Req 3, Req 5 — issue AC-2)*
- [ ] **AC-3**: In the AC-1 traces, every drive oscillates — no drive is monotone-increasing to a pinned maximum over the run (spec-032-AC-5-style check applied to the cc=3 run). *(maps to Req 4 — issue AC-3)*
- [ ] **AC-4**: Deterministic test: `DriveDecaySystem` with 3 active agents decays each agent at `decayRate/3` per second; with 1 active agent at `decayRate`; with `ENGINE_DECAY_SCALING='none'` at the raw rate regardless of `N`. At `N=1` per-agent decay is bit-identical to the pre-change path (spec-019 test fixtures still pass unmodified — `DriveSystemImpl.applyDecay` is untouched). *(maps to Req 1)*
- [ ] **AC-5**: Deterministic economy-audit test: for every drive key, `max(restoring effects delta in DYNAMIC_WORLD_SCENE) > configuredDecayRate / 3 × meanCycleInterval`, with `meanCycleInterval` derived from the scene's scheduler config and scene duration; the test names the failing (affordance, drive) pair on failure. *(maps to Req 2)*
- [ ] **AC-6**: Deterministic matcher test: for an agent with hunger < 40, the matcher surfaces `plant_seeds` and `harvest` as chain-progress hints for hunger (ranked with, and after, any direct-restoration hints); no chain hint when hunger ≥ 40; no chain hint for `social` even if declared; the `progresses` field is absent on other affordances and produces no hint. *(maps to Req 3)*
- [ ] **AC-7**: `pnpm -r test && pnpm typecheck && pnpm lint` pass; spec-019/032/034 existing tests pass unmodified except where this spec's additive changes extend them; the coffee-shop and morning-routine scenes are untouched. *(maps to Req 1, Req 2, Req 3)*

## Constraints
- **`engine`**: changes confined to `DriveDecaySystem` + config plumbing (`EngineConfig`/`assembly.ts`/`createEngineCore`). Do **not** touch `DriveSystemImpl.applyDecay`'s signature or semantics — the spec-019 test suite is its contract. Do **not** change the default `decayRate` of 0.1 (spec 019).
- **`shared`**: the `Affordance.progresses` field is additive and optional; no existing field changes meaning; legacy fixtures omitting it must behave exactly as today.
- **`cognition`**: the matcher stays a pure, synchronous function of (drives, perceived affordances), O(drives × affordances), no caching, no async (spec 034 Constraints). The `social` drive remains excluded from all hint paths (spec 034/047).
- **`examples`**: scene-level declarations only (`progresses` on `plant_seeds`/`harvest`, economy-table docs); reuse the existing `makeObject`/`aff` factories and handler placement — no new handlers, no parallel registration shadowing builtin plugins (spec 032 Constraints).
- **Determinism**: AC-4/5/6/7 run without LLM calls; only AC-1/2/3 require a real LLM and are recorded as issue evidence.
- **Patterns to follow**: config plumbing via env → `EngineConfig` exactly like `ENGINE_MAX_CONCURRENT_LLM` (spec 022) and `DRIVE_DECAY_RATE` (spec 019); hint rendering exactly like spec 034's `formatPerceptionDriveHint`/`formatPlanDriveHint` (perception = suggestion form, plan = imperative form).
- **What NOT to do**: do not hardcode a drive→chain-step table in cognition (spec 034 Req 3); do not fake chain progress by adding small positive hunger `effects` to `plant_seeds` (it would misreport a restoration that doesn't happen); do not gate restoration on state counters (`seeds_planted`/`vegetables`) — rejected in spec 032; do not scale decay by `maxConcurrentCycles` instead of live agent count (dormant/late-spawned agents would skew the divisor); do not raise restoration magnitudes preemptively without a failing audit row (over-tuning kills the AC-3 oscillation).
