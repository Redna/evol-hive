# Feature: talk_to Target Resolution — Display Names Must Never Create Phantom Participants; `sentiment` Must Reach the Executor

> Issue: [#173](https://github.com/Redna/evol-hive/issues/173) — "live talk_to targets resolve to
> display names (phantom participants) and the sentiment argument is dropped — spec 033/043/044
> conversation behavior can't fully manifest even with the bridge wired." Discovered during the
> spec 045 live validation run (PR #172, 2026-09-10). Root-cause candidate for #167 (reply rate 0
> across all runs): the real target never receives anything.

No `examples/` changes required — spec 045's wiring is correct and stays untouched.

## Verified root cause (live evidence, session log 2026-09-10)

- Perception renders agents by display name only: `Agents present: Bob (idle)` (`packages/cognition/src/pper/perception-builder.ts:82`), while the `talk_to` schema asks for `targetAgentId` — "The ID of the agent" (`packages/shared/src/schemas/llm-schemas.ts:475`). Nothing resolves name→ID anywhere in the tool-call path: `openai-client.ts` mid-loop passes the raw string, `CognitiveToolExecutorImpl.executeTalkTo` does not normalize, `ConversationManagerImpl.open()` adds the target as a participant with no existence check (`conversation-manager.ts:310`).
- Live result: `[social] agent-alice talk_to→Bob ("Hey Bob! …")` — participant and relationship entries keyed to phantom `"Bob"`, `queueMessage('agent-alice','Bob',…)` delivers to a phantom key. The REAL Bob (`agent-bob`) is never a participant, so: the R7 co-location sweep closes the thread within one tick (phantom has no agent state → location undefined ≠ roomId); `getConversationsAwaitingAgentReply('agent-bob')` → `[]` always (spec 043 pending-address line never renders); a reply from Bob opens a NEW thread with phantom `'Alice'` — threads never extend. Every live conversation is structurally one-turn (symptom family of #165/#167).
- Gap 2: the mid-loop tool-call path (`openai-client.ts:662`) drops the LLM's `sentiment` tool arg (spec 033) — `result = await executor.executeTalkTo(agentId, targetAgentId, message)` — so every live exchange is tagged `neutral` and the delta is always the neutral branch (`+5/+2`, coinciding with legacy constants by design; only a negative-dominant exchange would differ).

## Requirements

- **R1 — Name→ID resolution on the social bridge.** `SocialActionBridge` (shared) gains `resolveAgentId(requesterAgentId: string, nameOrId: string): string | null`. `SocialManager` (engine) implements it: exact agent-ID passthrough first (an active agent state exists with that ID); otherwise case-insensitive match on `profile.name` over active agents, preferring agents co-located with the requester; `null` when nothing unambiguous matches. Resolution is deterministic — no LLM anywhere. (AC-1, AC-7, AC-8)

- **R2 — Executor-side normalization (the single choke point).** `CognitiveToolExecutorImpl` normalizes `targetAgentId` through `resolveAgentId` **before** any dispatch, for `talk_to` **and** the sibling social tools `observe_agent` / `help` / `ignore` (they share the identical phantom-key failure mode). All downstream consumers then use the resolved real ID: `openOrContribute`, `queueMessage`, `updateRelationship`, and the `[social]` telemetry line. Unresolvable targets return the structured failure result with an actionable message (naming the present agents) so the LLM self-corrects — no phantom keys are ever written. (AC-1, AC-2, AC-3, AC-4, AC-7, AC-8)

- **R3 — Engine-side tolerance in the conversation manager (belt-and-braces).** `ConversationManagerImpl.openOrContribute`/`open`/`contribute` resolve a participant key that matches no active agent ID by case-insensitive profile name via its own `agentManager` — so phantom participants are impossible even for direct bridge consumers (tests, future callers). The `ConversationBridge` interface (shared) is unchanged. If even name resolution fails, `open`/`contribute` return `success: false` rather than creating a phantom participant. (AC-1, AC-9)

- **R4 — Perception renders real IDs (spec 043 territory).** The `Agents present:` line becomes `Agents present: Bob (agent-bob) (idle)` — agent IDs visible so the LLM can pass real IDs directly and duplicate display names stay unambiguous. The line remains in the stable (above `---`) section: it is still a pure function of room membership + activity, and IDs are exactly as stable as names (spec 021 rules respected — structure unchanged, no cache regression). Pinned prompt-string tests are updated with the change. (AC-6)

- **R5 — `sentiment` passthrough in the tool-call loop.** The mid-loop `talk_to` branch in `openai-client.ts` extracts the `sentiment` tool arg, validates it against the spec 033 enum (`positive` | `neutral` | `negative`), defaults to `neutral` on absence/invalid values, and passes it as the fourth argument to `executeTalkTo` (the executor signature already accepts it). A unit test pins the arg mapping. (AC-5)

- **R6 — No regressions, legacy path preserved.** The legacy blind `+5/+2` fallback in `executeTalkTo` remains for contexts wired without a conversation bridge (spec 033 AC-14). Spec 045/044/033 tests pass unmodified; full suite green. Exact-ID targeting (well-behaved LLM passing `agent-bob`) behaves identically to today, minus nothing. (AC-9, AC-10)

## Acceptance Criteria

- [ ] **AC-1** (R1, R2, R3): `talk_to` with a display-name target (`'Bob'`) through the production-constructed executor results in a conversation whose participants are the REAL agent IDs (`['agent-alice','agent-bob']`, not a phantom `'Bob'`), and the thread survives the R7 co-location sweep while both agents remain in the room (status stays `open`/`active` past the tick in which it was opened). Deterministic test — no LLM.
- [ ] **AC-2** (R2): after the resolved-ID `talk_to`, the target's `queueMessage` key is the real ID — `getConversationsAwaitingAgentReply('agent-bob')` returns the conversation, and the target's next perception renders the spec 043 pending-address line quoting the actual message (deterministic; the live-run audit is a manual follow-up on the issue).
- [ ] **AC-3** (R2): a reply from the resolved target via `talk_to` extends the SAME thread — `turnCount ≥ 2`, status transitions `open → active` per spec 033 lifecycle — instead of opening a new phantom-keyed thread. Deterministic test.
- [ ] **AC-4** (R2): the real target's `receivedCount` increments on their contribution (spec 044 R2 reciprocity observable with resolved keys).
- [ ] **AC-5** (R5): unit test on the tool-call loop arg mapping — an LLM tool-call with `sentiment: 'negative'` reaches `executeTalkTo` as `'negative'`; missing/invalid values map to `'neutral'`.
- [ ] **AC-6** (R4): the perception payload contains `Agents present: Bob (agent-bob) (idle)`-style lines (ID included); every prompt-pinning test updated; the line stays above the `---` cache boundary and its structure is unchanged.
- [ ] **AC-7** (R1, R2): `observe_agent` / `help` / `ignore` with a display-name target resolve to real IDs — no phantom keys in relationship maps or the message queue for any social tool.
- [ ] **AC-8** (R1, R2): an unresolvable target (`'Zed'`, no match) yields a structured failure result whose message lists the present agents (Req 17 self-correction), and writes NO conversation, relationship, or queued message under any key.
- [ ] **AC-9** (R3, R6): a direct `openOrContribute` call with a display-name key on the bare `ConversationManagerImpl` (no executor) also resolves to the real ID; unresolvable keys fail with `success: false` — no phantom participant is ever created. `ConversationBridge` interface unchanged.
- [ ] **AC-10** (R6): full suite green (`pnpm test`); spec 033 lifecycle/bridge tests, spec 044 counter tests, and spec 045 assembly tests pass **unmodified**; exact-ID targeting unchanged (regression test with `targetAgentId: 'agent-bob'` behaves as before).

## Constraints

- **Package boundaries**: `shared` (interface method + schema docs only), `engine` (`SocialManager`, `ConversationManagerImpl`), `cognition` (`cognitive-tool-executor.ts`, `llm/openai-client.ts`, `pper/perception-builder.ts`). No `examples/` changes (spec 045 wiring is correct); no `memory` changes.
- **Determinism**: resolution is pure TypeScript over `agentManager` profiles/states — no LLM anywhere (AC-14 discipline; ADR-0001 bridge pattern: interface in shared, engine implements, cognition consumes).
- **KV-cache rules (spec 021)**: the `Agents present` line stays above `---`; adding IDs must not change line structure or ordering. Do NOT touch the `tools` array, tool schemas' shape (a doc-only description tweak on `targetAgentId` is allowed), or the PPER loop.
- **Failure semantics**: unresolvable targets must fail loudly with actionable feedback (Req 17 pattern) — never silently drop, never fall back to the raw string.
- **What NOT to do**: do not fix this prompt-only (perception IDs alone don't guarantee the LLM passes IDs — resolution remains the safety net); do not create a second `ConversationManagerImpl` or re-wire spec 045's assembly; do not change the `ConversationBridge` interface; do not alter conversation close-time consolidation or the R7 sweep itself; do not key anything (participants, relationships, queue, telemetry) to un-resolved strings.
