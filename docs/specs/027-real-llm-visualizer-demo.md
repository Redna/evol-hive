# Feature: Real-LLM Visualizer Demo — Wire PPER Cycles into the Canvas Visualizer

## Context
- Architecture: [§2 — System Overview](../architecture/02-system-overview.md) (package boundaries, example entry points as composition roots), [§4 — Smart Objects & Affordances](../architecture/04-smart-objects.md) (affordance execution, object state rules — live object state on canvas), [§6 — PPER Loop](../architecture/06-pper-loop.md) (perceive→plan→execute→reflect cycles the demo must run), [§9 — Engine Routing](../architecture/09-engine-routing.md) (asynchronous state management, agent movement via `go_to_*` doorway affordances), [§10 — Cognitive Guardrails](../architecture/10-cognitive-guardrails.md) (guardrail engine wired into the real orchestrator)

## Design Rationale

The visualizer demo (spec 023) currently uses a no-op `MockOrchestrator`: `runCycle()` returns immediately, so agents never act. The canvas shows decaying drive bars over a static scene — a rendering demo, not a behavior demo. Verifying emergent behavior (navigation, coffee brewing, relationship formation) still requires reading headless validation logs.

The fix is composition, not new subsystems. All the pieces already exist and are proven in `examples/coffee-shop.ts` (spec 019):

**1. Reuse `buildCoffeeShopEngine()`'s assembly by extracting it, not duplicating it.** The real-LLM wiring in `coffee-shop.ts` (memory store → engine core → SocialManager → LLM client → classifier → guardrail → `createPPEROrchestrator` → memory decay + reflection loop → `assembleGameLoop`) is ~120 lines of careful subsystem plumbing. Copying it into `visualizer-demo.ts` would create two wiring code paths that drift apart — exactly the failure mode that makes demo and validation diverge. Instead, the cognition/memory assembly is extracted into a shared helper module (`examples/assembly.ts`) exporting `assembleCognitionStack(core, socialManager, options)`, and `buildCoffeeShopEngine()` is refactored to call it. The visualizer demo calls the same helper. Both entry points then share one wiring source of truth for LLM/guardrail/tool-executor assembly. This is a pure refactor for `coffee-shop.ts`: `CoffeeShopAssembledEngine` keeps its exact shape and all spec-019 tests pass unchanged.

**2. YAML scenes as the single source of truth.** The demo currently imports `COFFEE_SHOP_SCENE` from `coffee-shop.ts` while the CLI (`run-scene`, `validate-scene`) loads `examples/coffee-shop.scene.yaml` (spec 022). Two representations of the same scene invite divergence. The demo loads `coffee-shop.scene.yaml` via `loadSceneFile()` + `autoRegisterHandlers()` — the exact path the CLI uses — so what the visualizer renders is byte-for-byte the scene that headless validation runs. The inline `MINIMAL_SCENE` / `MORNING_ROUTINE_SCENE` definitions remain TypeScript (they are demo-only scenes with no validation counterpart), keeping the change minimal.

**3. Env-var convention identical to `coffee-shop.ts`.** `USE_REAL_LLM=true` builds a real `PPEROrchestrator` (`OpenAICompatibleLLMClient` + `GuardrailEngineImpl` + `CognitiveToolExecutorImpl`); `USE_REAL_EMBEDDINGS=true` upgrades the classifier/embedding provider. Supporting env vars (`LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`, `LLM_REASONING_EFFORT`, `LLM_MAX_TOOL_CALL_ITERATIONS`, `EMBEDDING_MODEL_PATH`, `EMBEDDING_TOKENIZER_PATH`) are read by the shared assembly helper, so both entry points honor them identically. Default (no env vars) behavior is unchanged: mock orchestrator, zero network calls.

**4. Startup LLM health check in real mode.** A real-LLM run against an unreachable backend would otherwise look identical to the old bug — a static scene with decaying bars. In real mode, the demo performs a trivial `completeStructured` probe (or a TCP reachability check on `LLM_BASE_URL`) at startup and exits with a clear error naming the backend URL if it fails. This converts the issue's silent-failure mode ("agents never act") into a loud one.

**5. Movement rendering is already supported.** The renderer (spec 023) draws agents in their current room and the adapter snapshots `location` per agent. Agent movement between rooms happens through the engine's existing `go_to_<room>` doorway affordances executed by the PPER loop (§9.2 action feedback loop) — no visualizer changes are needed for AC-2. The only deliverable is making PPER cycles actually run against the loaded scene.

## Requirements

### Shared Assembly (`examples/`)

1. **Extract cognition assembly helper** — Create `examples/assembly.ts` exporting an `assembleCognitionStack()` function that encapsulates the subsystem wiring currently inlined in `buildCoffeeShopEngine()`: memory store/vector store/embedding provider construction, LLM client selection (`USE_REAL_LLM`), `CognitiveToolExecutorImpl` construction, `AffordanceClassifier` selection (`USE_REAL_EMBEDDINGS`), `GuardrailEngineImpl` construction, `createPPEROrchestrator(...)` invocation, and (optionally, per options) memory decay service + reflection loop wiring. It accepts an assembled `EngineCore` + `SocialManager` (or constructs the SocialManager itself) and returns the same fields `CoffeeShopAssembledEngine` adds beyond `AssembledEngine` (`llmClient`, `guardrail`, `classifier`, `embeddingProvider`, `vectorStore`, `cognitiveToolExecutor`, `memoryDecayService`, `reflectionLoop`, `orchestrator`). All `USE_REAL_LLM`/`USE_REAL_EMBEDDINGS`/`LLM_*`/`EMBEDDING_*` env vars are read here — one place, both entry points.

2. **Refactor `buildCoffeeShopEngine()` onto the helper** — `examples/coffee-shop.ts` `buildCoffeeShopEngine()` must delegate its cognition/memory wiring to `assembleCognitionStack()`. The returned `CoffeeShopAssembledEngine` interface, returned fields, scene loading (`COFFEE_SHOP_SCENE`), handler registration (`registerAffordanceHandlers` + `registerCoffeeShopHandlers`), auto-save wiring, and game-loop assembly stay exactly as they are. All existing coffee-shop tests pass without modification.

3. **Real orchestrator in the visualizer demo** — When `USE_REAL_LLM=true`, `examples/visualizer-demo.ts` must build a real `PPEROrchestrator` (via `assembleCognitionStack()`) wired to `core.bridges.{perceive,plan,execute,reflect}` and pass it to both `assembleGameLoop()` and the `VisualizerDataAdapter` (so `getPhase()` reports live phases). The `MockOrchestrator` remains the default when the env var is unset or not `'true'`.

4. **Demo handler parity** — In real mode the demo must register the same affordance handlers the coffee-shop validation scene uses, via the spec-022 plugin path (`clearHandlerPlugins()` + `createBuiltinPlugins()` + `registerHandlerPlugin()` + `autoRegisterHandlers(core)` or the equivalent `registerCoffeeShopHandlers`), so `brew_coffee`, `add_water`, `go_to_*` doorway affordances, social handlers, and object state rules all execute.

### Scene Loading (`examples/`)

5. **Load coffee-shop scene from YAML** — `visualizer-demo.ts` must load the coffee-shop scene with `loadSceneFile('examples/coffee-shop.scene.yaml')` (path resolvable from repo root) instead of importing `COFFEE_SHOP_SCENE` from `coffee-shop.ts`. The YAML file is the single source of truth shared with `evol-hive run-scene` / `validate-scene`.

6. **Demo scene map integrity** — The demo's scene map continues to expose `minimal`, `morning-routine`, and `coffee-shop`. The `coffee-shop` entry is built from the YAML load (Req 5); the other two keep their existing inline definitions. Selecting any scene and running with `USE_REAL_LLM=true` must start PPER cycles for that scene's agents (the assembly is scene-agnostic).

### Real-LLM Runtime Behavior

7. **Agents perform PPER cycles and move** — With `USE_REAL_LLM=true`, agents must execute full perceive→plan→execute→reflect cycles through the real orchestrator: they navigate between rooms via `go_to_*` doorway affordances (kitchen ↔ living_room at minimum), execute object affordances such as `brew_coffee`, and form/update relationships through the SocialManager — matching the behavior observed in headless validation runs of the same scene.

8. **Live state visible in snapshots** — Affordance executions must mutate state that the `VisualizerDataAdapter` snapshots render live: object state (e.g., `water_level` decreasing on the coffee machine), agent drives (energy/social bars changing from executed affordance `driveChanges`), agent `location` (room changes), and `orchestrator.getPhase()` phase transitions. This requires no renderer changes — only that the real orchestrator drives the same engine state the adapter already reads.

9. **Startup LLM health check** — When `USE_REAL_LLM=true`, the demo must verify the LLM backend is reachable at startup (probe `LLM_BASE_URL` / `completeStructured`) and exit with a non-zero code and an error message that includes the backend URL and model if unreachable. No health check and no network calls occur in default (mock) mode.

10. **Concurrent-cycles safety** — The demo runs 3 coffee-shop agents with `maxConcurrentLLM: 8` (existing config) and the existing game-loop scheduling. Real-mode must not introduce new concurrency beyond what `coffee-shop.ts` already exercises (no changes to engine loop or orchestrator scheduling).

## Acceptance Criteria

- [ ] AC-1 (Req 1, 2): `examples/assembly.ts` exists and exports `assembleCognitionStack()`; `buildCoffeeShopEngine()` in `examples/coffee-shop.ts` contains no direct `OpenAICompatibleLLMClient` / `GuardrailEngineImpl` / `createPPEROrchestrator` construction — it calls the helper. All existing `spec-019` coffee-shop tests pass unchanged, and `CoffeeShopAssembledEngine`'s public shape is unchanged.
- [ ] AC-2 (Req 3): With `USE_REAL_LLM=true`, `startVisualizerDemo()` returns a handle whose orchestrator is a real `PPEROrchestrator` (constructed via `createPPEROrchestrator`, holding an `OpenAICompatibleLLMClient` and `GuardrailEngineImpl`), and `adapter` snapshots report non-static `getPhase()` values. With the env var unset, the orchestrator is the `MockOrchestrator`. Verified by unit test constructing the demo with each env setting and asserting on the returned handle's `orchestrator` type.
- [ ] AC-3 (Req 5): `visualizer-demo.ts` contains no import of `COFFEE_SHOP_SCENE` from `./coffee-shop.js`; it calls `loadSceneFile()` with the `examples/coffee-shop.scene.yaml` path. A unit test loads the same file via the demo's scene-building function and asserts the resulting `SceneDefinition` has id `coffee-shop`, the 4 YAML rooms (kitchen, living_room, bathroom, garden), and the YAML object set.
- [ ] AC-4 (Req 6): The demo's scene map contains all three scenes; the `coffee-shop` entry is deep-equal to the YAML-loaded scene (per AC-3), and `minimal`/`morning-routine` load and render as before (existing visualizer demo smoke tests still pass).
- [ ] AC-5 (Req 4, 7, 8): Integration test (mock-LLM variant of the shared assembly, real orchestrator with a scripted/mock LLM): after running the game loop for N ticks with the coffee-shop YAML scene, at least one agent's `location` changes between `kitchen` and `living_room`, the coffee machine's `water_level` decreases below its initial value of 5, and at least one agent's drive values change from executed affordance `driveChanges`. This proves the state the visualizer renders reflects executed PPER cycles.
- [ ] AC-6 (Req 7): Manual verification recorded in the issue: `USE_REAL_LLM=true npx tsx examples/visualizer-demo.ts` against a running Ollama backend starts without errors, and within a few minutes of wall-clock time the canvas shows (a) an agent moving between rooms, (b) the coffee machine's water level decreasing while Alice brews, (c) drive bars responding to executed affordances, (d) relationship lines appearing/changing between agents.
- [ ] AC-7 (Req 9): With `USE_REAL_LLM=true` and `LLM_BASE_URL` pointing at an unreachable port, the demo exits non-zero and its error output includes the configured backend URL. With the env var unset, the demo starts with no network activity (no socket connections attempted) — verified by test.
- [ ] AC-8 (Req 10): All existing tests pass (`pnpm test`). The change touches only `examples/` (plus the new `examples/assembly.ts`); no package source files under `packages/` are modified. The default visualizer demo (no env vars) behaves identically to before: mock orchestrator, static-agent scene with decaying drive bars, no LLM required.
- [ ] AC-9 (Req 1, 2, 7): Env-var parity test: with `USE_REAL_LLM=true` and identical `LLM_*` env vars, `assembleCognitionStack()` used by `buildCoffeeShopEngine()` and by the visualizer demo produces an `llmClient` configured with the same `baseUrl` and `model`. Verified by constructing both paths with the same env and asserting on the returned client config.

## Constraints
- **Scope: `examples/` only.** No source changes to `@evol-hive/shared`, `@evol-hive/engine`, `@evol-hive/cognition`, `@evol-hive/memory`, or `@evol-hive/visualizer`. The refactor is confined to `examples/coffee-shop.ts`, `examples/visualizer-demo.ts`, and the new `examples/assembly.ts` (which may import from the existing packages only).
- **Preserve spec-019/023 behavior.** `CoffeeShopAssembledEngine` keeps its exact interface; `startVisualizerDemo()` keeps its signature and `VisualizerDemoHandle` shape (fields may be added, none removed). Default-mode demos need no Ollama, no embeddings, and no network.
- **Follow the `USE_REAL_LLM` convention** exactly as defined in `coffee-shop.ts` (spec 019): env var `=== 'true'`, default `LLM_BASE_URL` `http://localhost:11434/v1`, default model `llama3.1`. Do not invent new env var names for existing knobs.
- **YAML is the coffee-shop source of truth** (spec 022). Do not regenerate or edit `coffee-shop.scene.yaml` as part of this feature; the demo consumes it as-is. Do not convert `MINIMAL_SCENE`/`MORNING_ROUTINE_SCENE` to YAML in this spec (out of scope; demo-only scenes).
- **What NOT to do:**
  - Do NOT duplicate the coffee-shop assembly logic inside `visualizer-demo.ts` — copy-paste wiring is the divergence this spec exists to prevent.
  - Do NOT change the visualizer renderer, WebSocket transport, or `VisualizerState` schema; movement and live state already render from snapshots.
  - Do NOT run PPER cycles in mock mode (no timers, no simulated cycles) — the no-op `MockOrchestrator` default stays a no-op so the mock demo remains deterministic for smoke tests.
  - Do NOT add new npm dependencies; the demo already has access to `loadSceneFile` and the cognition classes via workspace packages.
  - Do NOT block the game loop on LLM calls beyond the existing `maxConcurrentLLM` scheduling (§9 concurrency control).
