# Feature: Object Interactions — Multi-Step Affordances, Object State Changes, Dependencies

## Context
- Architecture: [§4 — Smart Objects & Affordances](../architecture/04-smart-objects.md) (SmartObject, Affordance, preconditions, engineEffect, execution flow), [§5 — Fast-Path Classifier](../architecture/05-fast-path-classifier.md) (affordance pruning by semantic relevance), [§6 — PPER Loop](../architecture/06-pper-loop.md) (Perceive → Plan → Execute → Reflect), [§9 — Engine Routing](../architecture/09-engine-routing.md) (isThinking, action feedback loop)
- Related specs: [003 — Execute Phase](003-execute-phase.md) (PhysicsSystemImpl, precondition checking, AffordanceHandler, AffordanceResult, ExecuteDataProvider), [013 — Richer Prototype Scenes](013-richer-prototype-scenes.md) (scene definitions, affordance handlers, precondition checkers, object state depletion), [001 — Perceive Phase](001-perceive-phase.md) (PerceptionDataProvider, PerceptionResult, classifier integration), [002 — Plan Phase](002-plan-phase.md) (PlanBuilder, LLMContextPayload, formulate_plan)
- Package: `shared` (type extensions), `engine` (object state system, conditional filtering, cross-object state changes, registry extensions), `cognition` (classifier integration, plan builder context)
- ADR: [ADR-0001 — Lean Monorepo Structure](../adr/0001-lean-monorepo-structure.md)
- Issue: [#63](https://github.com/Redna/evol-hive/issues/63)

## Design Rationale

The current Smart Object system (§4) supports simple affordances with string-based preconditions and flat object state, but lacks five capabilities identified in issue #63:

1. **Object State Evolution** — Objects have state but it only changes via affordance execution (`newState` in `AffordanceResult`). There is no mechanism for autonomous state changes over time (e.g., a coffee machine cooling down, a plant growing). We add an `ObjectStateSystem` engine system — following the `DriveDecaySystem` pattern (spec 005) — that applies declarative `ObjectStateRule`s each tick.

2. **Multi-Step Affordances** — The plan system already sequences `PlanStep`s with `targetAffordance`. The gap is that the LLM has no metadata about which affordances form a logical sequence (e.g., `add_water` → `add_beans` → `press_brew` → `pour_cup`). We add `stepGroup`/`stepOrder` fields to `Affordance` and a `CompoundAction` type on `SmartObject` so the plan builder can inform the LLM about multi-step sequences. No changes to the Execute phase are needed — each step remains a single affordance execution.

3. **Object Dependencies** — No mechanism exists for declaring that one object's affordance depends on another object (e.g., Coffee Machine needs water from Sink). We add an `ObjectDependency` type on `SmartObject` and surface dependency information in the plan builder's LLM context so the LLM can plan cross-object interactions.

4. **Conditional Affordances** — Preconditions are checked at execute time (fail → system feedback). The classifier (§5) receives *all* affordances in a room regardless of whether their preconditions are currently satisfied. This wastes classifier budget on unavailable affordances and can mislead the LLM into planning actions that will fail. We add structured `conditions` on `Affordance` and a new `getAvailableAffordancesInRoom` method that filters affordances whose conditions are not met, used by the perception service before classifier pruning.

5. **Object Replenishment** — Handlers can only modify the state of the object they're called on (`newState` in `AffordanceResult`). Cross-object replenishment (e.g., `refill_water` on Sink updating the Coffee Machine's `water_level`) requires a handler to modify another object's state. We add `crossObjectStateChanges` to `AffordanceResult` and have `PhysicsSystemImpl` apply them via `SmartObjectRegistry.updateState`.

All changes are backward-compatible: new fields are optional, new methods have default fallbacks, and existing scenes/handlers continue to work without modification.

## Requirements

### Shared Layer (`@evol-hive/shared`)

1. **`AffordanceCondition` type** — A new interface `AffordanceCondition` must be defined in `packages/shared/src/types/affordance.ts` representing a structured condition evaluated against a smart object's `state`: `{ field: string; operator: '>' | '<' | '>=' | '<=' | '==' | '!='; value: number | string | boolean }`. The `field` is a key in `SmartObject.state`, the `operator` is a comparison, and the `value` is the comparison target. This is a declarative, self-describing condition that the engine can evaluate without a registered checker — unlike `preconditions: string[]` which require a registered `PreconditionChecker`.

2. **`stepGroup` and `stepOrder` on `Affordance`** — Add optional fields `stepGroup?: string` and `stepOrder?: number` to the `Affordance` interface in `packages/shared/src/types/affordance.ts`. `stepGroup` is a semantic group name (e.g., `"brew_coffee_sequence"`) linking related affordances into a multi-step sequence. `stepOrder` is a 1-based ordinal indicating the step's position within the group. Affordances without `stepGroup` are standalone and not part of any sequence.

3. **`CompoundAction` type** — A new interface `CompoundAction` must be defined in `packages/shared/src/types/affordance.ts`: `{ id: string; label: string; steps: { affordanceId: string; description: string }[] }`. The `id` is a semantic name (e.g., `"brew_coffee"`), `label` is a human-readable description, and `steps` is an ordered list mapping to affordance IDs on this object. This provides the LLM with a high-level view of multi-step sequences.

4. **`ObjectDependency` type** — A new interface `ObjectDependency` must be defined in `packages/shared/src/types/affordance.ts`: `{ affordanceId: string; requiresObjectId: string; requiresAffordance: string; description: string }`. `affordanceId` is the affordance on this object that has the dependency. `requiresObjectId` is the ID of the object that must be interacted with first. `requiresAffordance` is the affordance on the required object that must be executed first. `description` is a human-readable explanation for the LLM context.

5. **`ObjectStateRule` type** — A new interface `ObjectStateRule` must be defined in `packages/shared/src/types/affordance.ts`: `{ field: string; operation: 'decay' | 'approach'; rate: number; target?: number; interval: number }`. For `operation: 'decay'`, the rule subtracts `rate * deltaSeconds` from `state[field]` each interval (clamped to ≥ 0). For `operation: 'approach'`, the rule moves `state[field]` toward `target` by `rate * deltaSeconds` each interval (clamped to not overshoot). `interval` is the minimum time in seconds between applications (throttling). `field` is a key in `SmartObject.state` whose value must be a number.

6. **`stateRules`, `compoundActions`, `dependencies` on `SmartObject`** — Add optional fields to the `SmartObject` interface in `packages/shared/src/types/affordance.ts`: `stateRules?: ObjectStateRule[]`, `compoundActions?: CompoundAction[]`, `dependencies?: ObjectDependency[]`. All are optional — existing `SmartObject` definitions without these fields compile without modification.

7. **`conditions` on `Affordance`** — Add an optional field `conditions?: AffordanceCondition[]` to the `Affordance` interface in `packages/shared/src/types/affordance.ts`. When present, these structured conditions are evaluated at perception time to determine if the affordance is currently available. When absent, the affordance is always considered available (subject to classifier pruning). This is distinct from `preconditions: string[]`, which are evaluated at execute time as a fail-safe.

8. **`CrossObjectStateChange` type** — A new interface `CrossObjectStateChange` must be defined in `packages/shared/src/types/affordance.ts`: `{ objectId: string; statePatch: Record<string, unknown> }`. `objectId` is the ID of another `SmartObject` whose state should be modified. `statePatch` is a partial state object — the engine merges these fields into the target object's existing state (shallow merge, not full replacement).

9. **`crossObjectStateChanges` on `AffordanceResult`** — Add an optional field `crossObjectStateChanges?: CrossObjectStateChange[]` to the `AffordanceResult` interface in `packages/shared/src/types/affordance.ts`. When present and the affordance execution succeeds, the engine applies each cross-object state change by merging `statePatch` into the target object's state via `SmartObjectRegistry.updateState`. When absent or empty, no cross-object changes are applied. This enables replenishment scenarios (e.g., `refill_water` on a Sink updating a Coffee Machine's `water_level`).

10. **`CompoundActions` and `ObjectDependencies` on `PerceptionResult`** — Add optional fields `compoundActions?: CompoundAction[]` and `objectDependencies?: ObjectDependency[]` to the `PerceptionResult` interface in `packages/shared/src/types/cognition.ts`. `compoundActions` contains all compound actions defined on objects in the agent's current room. `objectDependencies` contains all dependencies declared by objects in the agent's current room. These are populated by the `PerceptionServiceImpl` and consumed by the `PlanBuilderImpl` to enrich the LLM context.

11. **`getAvailableAffordancesInRoom` on `PerceptionDataProvider`** — Add a new method to the `PerceptionDataProvider` interface in `packages/shared/src/types/cognition.ts`: `getAvailableAffordancesInRoom(roomId: string): Affordance[]`. This returns only affordances whose `conditions` (if present) are currently satisfied by the owning object's state. Affordances without `conditions` are always included. The existing `getAffordancesInRoom` method remains unchanged for backward compatibility.

12. **`getCompoundActionsInRoom` and `getObjectDependenciesInRoom` on `PerceptionDataProvider`** — Add two new methods to the `PerceptionDataProvider` interface in `packages/shared/src/types/cognition.ts`: `getCompoundActionsInRoom(roomId: string): CompoundAction[]` and `getObjectDependenciesInRoom(roomId: string): ObjectDependency[]`. These aggregate compound actions and dependencies across all objects in a room. Returns an empty array if no objects in the room define compound actions or dependencies.

### Engine Layer (`@evol-hive/engine`)

13. **`evaluateConditions` static helper** — A new static function `evaluateConditions(state: Record<string, unknown>, conditions: AffordanceCondition[]): boolean` must be implemented in `packages/engine/src/world/affordances/index.ts`. It evaluates each `AffordanceCondition` against the `state` object: extracts `state[condition.field]`, applies the `operator` against `condition.value`, and returns `true` only if all conditions pass. If the field is missing from state, the condition fails (returns `false`). The function handles type coercion for numeric comparisons (if both the state value and condition value are numbers, compare numerically; otherwise compare as-is).

14. **`SmartObjectRegistryImpl.getAvailableAffordancesInRoom`** — A new method `getAvailableAffordancesInRoom(roomId: string): Affordance[]` must be implemented on `SmartObjectRegistryImpl` in `packages/engine/src/world/objects/index.ts`. It iterates all objects in the room and for each affordance: if `affordance.conditions` is present and non-empty, evaluates them via `evaluateConditions(object.state, affordance.conditions)`; if the conditions pass (or are absent), the affordance is included. Affordances without `conditions` are always included. This method is the engine-side counterpart of `PerceptionDataProvider.getAvailableAffordancesInRoom`.

15. **`SmartObjectRegistryImpl.getCompoundActionsInRoom`** — A new method `getCompoundActionsInRoom(roomId: string): CompoundAction[]` must be implemented on `SmartObjectRegistryImpl`. It iterates all objects in the room and collects all `compoundActions` arrays, flattening them into a single array. Objects without `compoundActions` contribute nothing.

16. **`SmartObjectRegistryImpl.getObjectDependenciesInRoom`** — A new method `getObjectDependenciesInRoom(roomId: string): ObjectDependency[]` must be implemented on `SmartObjectRegistryImpl`. It iterates all objects in the room and collects all `dependencies` arrays, flattening them into a single array. Objects without `dependencies` contribute nothing.

17. **`SmartObjectRegistryImpl.applyStatePatch`** — A new method `applyStatePatch(objectId: string, patch: Record<string, unknown>): void` must be implemented on `SmartObjectRegistryImpl`. It performs a shallow merge of `patch` into the object's existing `state` (i.e., `{ ...existingState, ...patch }`), preserving fields not present in the patch. If the object does not exist, the method is a no-op. This is used by cross-object state changes (Req 20) and object state rules (Req 21). The existing `updateState` method (full state replacement) remains unchanged for backward compatibility.

18. **`SmartObjectRegistry` interface update** — The `SmartObjectRegistry` interface in `packages/engine/src/world/index.ts` must be extended with the four new methods: `getAvailableAffordancesInRoom(roomId: string): Affordance[]`, `getCompoundActionsInRoom(roomId: string): CompoundAction[]`, `getObjectDependenciesInRoom(roomId: string): ObjectDependency[]`, and `applyStatePatch(objectId: string, patch: Record<string, unknown>): void`.

19. **`PhysicsSystemImpl` — cross-object state changes** — The `executeAffordance` method in `packages/engine/src/physics/index.ts` must be extended to handle `crossObjectStateChanges` in the `AffordanceResult`. After the handler succeeds and the primary object's `newState` is applied (existing behavior), if `result.crossObjectStateChanges` is present and non-empty, the method must iterate each `CrossObjectStateChange` and call `this.smartObjectRegistry.applyStatePatch(change.objectId, change.statePatch)`. If a target object does not exist, the individual patch is silently skipped (no error thrown — the primary execution still succeeds). Cross-object state changes are only applied on success (`result.success === true`); on failure they are ignored.

20. **`ObjectStateSystem` — autonomous state evolution** — A new class `ObjectStateSystem` must be implemented in `packages/engine/src/systems/object-state.ts` following the `DriveDecaySystem` pattern (spec 005). It implements `EngineSystem` with `name = 'object-state'`. Its `update(tick: GameTick)` method iterates all smart objects in the registry (via a new `getAll()` method on `SmartObjectRegistryImpl` that returns all registered objects), and for each object with `stateRules`, applies each rule:
    - Track the last application time per rule (using a `Map<string, number>` keyed by `${objectId}:${field}`).
    - If `tick.time - lastApplied < rule.interval`, skip (throttling).
    - For `operation: 'decay'`: subtract `rule.rate * deltaSeconds` from `state[field]`, clamped to ≥ 0.
    - For `operation: 'approach'`: move `state[field]` toward `rule.target` by `rule.rate * deltaSeconds`, clamped to not overshoot `target`.
    - Apply the new state via `SmartObjectRegistryImpl.applyStatePatch(objectId, { [field]: newValue })`.
    - Update `lastApplied` to `tick.time`.
    If `state[field]` is not a number, the rule is silently skipped. The constructor accepts `SmartObjectRegistryImpl` as a dependency.

21. **`SmartObjectRegistryImpl.getAll`** — A new method `getAll(): SmartObject[]` must be implemented on `SmartObjectRegistryImpl`, returning all registered smart objects. This supports `ObjectStateSystem` iteration. The `SmartObjectRegistry` interface must be updated to include this method.

22. **`PerceptionDataProviderImpl` — new methods** — The `PerceptionDataProviderImpl` class in `packages/engine/src/agents/perception/index.ts` must implement the three new `PerceptionDataProvider` methods (Req 11, Req 12):
    - `getAvailableAffordancesInRoom(roomId)` → delegates to `this.smartObjectRegistry.getAvailableAffordancesInRoom(roomId)`.
    - `getCompoundActionsInRoom(roomId)` → delegates to `this.smartObjectRegistry.getCompoundActionsInRoom(roomId)`.
    - `getObjectDependenciesInRoom(roomId)` → delegates to `this.smartObjectRegistry.getObjectDependenciesInRoom(roomId)`.

### Cognition Layer (`@evol-hive/cognition`)

23. **`PerceptionServiceImpl` — use available affordances** — The `perceive` method in `packages/cognition/src/pper/index.ts` must call `this.options.provider.getAvailableAffordancesInRoom(passive.roomId)` instead of `this.options.provider.getAffordancesInRoom(passive.roomId)` when the method is available. If the provider does not implement `getAvailableAffordancesInRoom` (backward compatibility), it falls back to `getAffordancesInRoom`. The returned affordances are then passed to the classifier for semantic pruning as before.

24. **`PerceptionServiceImpl` — populate compound actions and dependencies** — The `perceive` method must call `this.options.provider.getCompoundActionsInRoom(passive.roomId)` and `this.options.provider.getObjectDependenciesInRoom(passive.roomId)` (with graceful fallback to empty arrays if the methods are not implemented). The results must be included in the returned `PerceptionResult` as `compoundActions` and `objectDependencies` fields (only included when non-empty).

25. **`PlanBuilderImpl` — compound actions in LLM context** — The `build` method in `packages/cognition/src/pper/plan-builder.ts` must check `perceptionResult.compoundActions`. When present and non-empty, it must append a context line to `contextLines` listing the compound actions: `"Multi-step actions available: <compoundAction.label> (<step count> steps), ..."`. This informs the LLM that certain affordances form sequences, enabling it to plan multi-step interactions.

26. **`PlanBuilderImpl` — object dependencies in LLM context** — The `build` method must check `perceptionResult.objectDependencies`. When present and non-empty, it must append a context line to `contextLines` listing the dependencies: `"Object dependencies: <dependency.description>, ..."`. This informs the LLM that certain affordances require interacting with another object first.

### Cross-Cutting

27. **Backward compatibility** — All new fields on existing interfaces (`Affordance`, `SmartObject`, `AffordanceResult`, `PerceptionResult`) are optional. All new methods on existing interfaces (`SmartObjectRegistry`, `PerceptionDataProvider`) have default fallback behavior in the cognition layer (feature-detection via `typeof method === 'function'`). Existing scenes (spec 013 — Morning Routine, Office Day) and their affordance handlers must compile and run without modification. The `brew_coffee` handler from spec 013 (which returns `newState` and `driveChanges`) continues to work — it simply does not use `crossObjectStateChanges` or `conditions`.

28. **Package boundaries** (per ADR-0001) — `cognition` and `engine` must not directly import from each other. All new types (`AffordanceCondition`, `CompoundAction`, `ObjectDependency`, `ObjectStateRule`, `CrossObjectStateChange`) are defined in `@evol-hive/shared`. The `PerceptionDataProvider` bridge (defined in `shared`) is extended with new methods; `PerceptionDataProviderImpl` (in engine) implements them; `PerceptionServiceImpl` (in cognition) consumes them. `ObjectStateSystem` and `PhysicsSystemImpl` live in engine and do not call cognition. `PlanBuilderImpl` lives in cognition and reads `PerceptionResult` fields defined in shared.

29. **Deterministic execution preserved** — Cross-object state changes applied by `PhysicsSystemImpl` are deterministic: the handler returns `crossObjectStateChanges` as data, and the engine applies them via `applyStatePatch`. No random number generation, no LLM calls, no external I/O inside the application logic. The same handler result produces the same state changes. `ObjectStateSystem` rules are deterministic functions of `(state, deltaSeconds)` — no randomness.

30. **No changes to Execute phase orchestration** — The `ExecuteServiceImpl` (spec 003) is not modified. Multi-step affordances are handled at the plan level (the LLM plans a sequence of steps, each targeting one affordance). The Execute phase processes one step per tick as before. Cross-object state changes are handled inside `PhysicsSystemImpl.executeAffordance`, which is called by the existing `ExecuteDataProviderImpl.executeAffordance` bridge — no new bridge methods are needed for execution.

31. **Classifier integration** — The classifier (§5) receives the already-filtered available affordances from the perception service. No changes to the `AffordanceClassifier` interface or `AffordanceClassifierImpl` are needed. The conditional filtering happens before the classifier is invoked, reducing the number of affordances the classifier must embed and score.

32. **ObjectStateSystem registration** — The `ObjectStateSystem` must be registered as an `EngineSystem` during engine assembly (in `packages/engine/src/assembly.ts` or the entry point). It runs every tick alongside `DriveDecaySystem` and `PPERScheduler`. Objects without `stateRules` are skipped (no-op). The system must be registered after `SmartObjectRegistry` is populated (i.e., after `loadScene`).

## Constraints

- **Package boundaries** (per ADR-0001): `cognition` and `engine` must **not** directly import from each other. All new types (`AffordanceCondition`, `CompoundAction`, `ObjectDependency`, `ObjectStateRule`, `CrossObjectStateChange`) are defined in `@evol-hive/shared`. The `PerceptionDataProvider` bridge is the only communication channel for perception-time data. `PhysicsSystemImpl` handles cross-object state changes internally — no new bridge methods on `ExecuteDataProvider`. `PlanBuilderImpl` reads `PerceptionResult` fields only.
- **Backward compatibility**: All new fields on existing interfaces are optional. All new methods on existing interfaces have graceful fallbacks in the cognition layer (feature detection via `typeof method === 'function'`). The existing `getAffordancesInRoom` method on both `SmartObjectRegistry` and `PerceptionDataProvider` is **not** removed or deprecated — it remains for engine-internal use and backward compatibility. Existing scenes, handlers, and tests from specs 003 and 013 must compile and pass without modification.
- **Deterministic execution**: Cross-object state changes and object state rules are deterministic. No random number generation, no LLM calls, no `Date.now()` inside handlers or rules. `ObjectStateSystem` uses `tick.time` and `tick.deltaSeconds` from the `GameTick` — it does not read the system clock. This is critical for reproducible simulations.
- **No Execute phase changes**: The `ExecuteServiceImpl` and `ExecuteDataProvider` are **not** modified. Multi-step affordances are handled at the plan level (LLM plans a sequence of `PlanStep`s). Cross-object state changes are applied inside `PhysicsSystemImpl.executeAffordance`, which is already called by the existing `ExecuteDataProviderImpl.executeAffordance` bridge method — no new bridge methods needed.
- **No classifier changes**: The `AffordanceClassifier` interface and `AffordanceClassifierImpl` are **not** modified. Conditional filtering happens before the classifier is invoked. The classifier still receives `Affordance[]` and returns `Affordance[]` — it just receives a pre-filtered list.
- **ObjectStateSystem is tick-driven**: State rules are applied per-tick via `update(tick: GameTick)`, following the `DriveDecaySystem` pattern. Rules are declarative data on `SmartObject.stateRules` — the system interprets them. No per-object handler registration is needed for autonomous state changes.
- **Shallow merge for state patches**: `applyStatePatch` performs a shallow merge (`{ ...existingState, ...patch }`). Nested objects in state are replaced, not deep-merged. This is sufficient for the prototype; deep merge is a future concern.
- **Condition evaluation is stateless**: `evaluateConditions` is a pure function of `(state, conditions)` — it does not modify state, does not require registration, and does not depend on engine subsystems. This contrasts with `preconditions` (string names requiring registered `PreconditionChecker`s). Both systems coexist: `conditions` for perception-time filtering, `preconditions` for execute-time fail-safe checks.
- **What NOT to do**:
  - Do not modify the `ExecuteServiceImpl`, `ExecuteDataProvider`, or the Execute phase orchestration flow.
  - Do not modify the `AffordanceClassifier` interface or `AffordanceClassifierImpl` class.
  - Do not remove or deprecate the existing `getAffordancesInRoom` method or the `preconditions: string[]` / `PreconditionChecker` system.
  - Do not implement a compound affordance executor — multi-step sequences are handled by the existing plan step system (one affordance per step).
  - Do not implement agent-to-agent dependencies — only object-to-object dependencies are in scope.
  - Do not implement deep state merging for `applyStatePatch` — shallow merge only.
  - Do not add `ObjectStateSystem` to the PPER scheduler or make it agent-aware — it operates on all objects globally each tick.
  - Do not implement condition evaluation for nested state fields (e.g., `state.thermostat.temperature`) — only top-level fields are supported.
  - Do not add new npm dependencies.
  - Do not modify the `AffordanceHandler` type signature — handlers still return `AffordanceResult` (which now optionally includes `crossObjectStateChanges`).
  - Do not implement persistence for object state rules or condition definitions — they are declarative on the `SmartObject` and loaded with the scene.
