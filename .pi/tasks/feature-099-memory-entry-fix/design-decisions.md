# Design Decisions — Feature 099: Memory Entry Fix

## Decision 1: Flatten the memory schema (Issue Solution A) as the primary fix
**Why**: The root cause is that gemma4 (31b) does not understand the nested `memoryEntry` object schema inside the `reflect` tool definition. Smaller models handle flat top-level fields far more reliably than nested objects. Flattening `memoryEntry` into `memoryContent`, `memoryImportance`, `memoryType`, `memoryLocation` directly addresses the root cause. This is the minimal change with the highest probability of success.

**Alternative considered**: Keep the nested schema and improve the prompt (tried — no improvement). Keep the nested schema and make it required (Issue Solution B — rejected, would break no-op ticks). Add a separate `store_memory` tool (Issue Solution D — rejected, requires multi-turn tool calls not supported in current architecture).

## Decision 2: Keep nested `memoryEntry` as backward-compat alias
**Why**: Larger models (e.g., GPT-4, Claude) may already produce the nested `memoryEntry` correctly. Removing it would break those models. The `completeReflect()` parser checks both flattened and nested fields, preferring flattened when both are present. Both paths produce the same internal `MemoryEntryInput`.

**Impact**: The `reflectSchema` is slightly larger (4 new top-level fields + existing nested object). This is acceptable — the schema is passed as tool `parameters`, not inlined in the prompt.

## Decision 3: Auto-fallback memory generation (Issue Solution C) as the secondary fix
**Why**: Even with flattening, some models may still omit memory fields. The acceptance criterion requires "at least 1 memory stored per agent per 60s run." The auto-fallback guarantees this by generating a basic memory from the execution result (affordance label, success/failure, location) when the LLM returns nothing. This is a safety net, not a replacement for LLM-driven memory.

**Design**: The fallback uses `executeResult.affordanceLabel` and `agentState.location` to produce content like `"Brew coffee in kitchen"` (success) or `"Failed to Brew coffee in kitchen"` (failure). Importance is 3 (success) or 5 (failure) — low, so the LLM's memories (when it provides them) take priority in retrieval scoring. The fallback is configurable via `autoMemoryFallback` (default `true`).

## Decision 4: Extend `ExecuteResult` with `affordanceId` and `affordanceLabel`
**Why**: The auto-fallback needs the affordance label to generate meaningful memory content. Currently `ExecuteResult` only contains the `AffordanceResult` (drive changes, failure reason, new state) — not the affordance ID or label. The `ExecuteServiceImpl` has access to `step.targetAffordance` (ID) and `resolved.affordance.label` (label). Adding these to `ExecuteResult` is a minimal, clean extension that makes the execution result self-describing.

**Alternative considered**: Have the `ReflectServiceImpl` look up the affordance from the agent's plan (`agentState.currentPlan.steps[currentStepIndex].targetAffordance`). Rejected — fragile (the step was already advanced by the execute service) and only gives the ID, not the label. The label requires resolving the affordance, which the reflect service cannot do without coupling to the engine's affordance registry.

## Decision 5: `memoryAutoGenerated` flag on `ReflectResult` for observability
**Why**: Tests and operators need to know whether a memory was LLM-provided or auto-generated. The `memoryAutoGenerated` boolean flag on `ReflectResult` makes this explicit without affecting control flow. This allows QA to measure the LLM's memory compliance rate over time.

## Decision 6: Reject making memoryEntry required (Issue Solution B)
**Why**: Forcing `memoryEntry` to be required would cause tool call validation failures when the LLM legitimately has nothing to record (e.g., skipped steps, idle ticks). This would break the PPER cycle. The auto-fallback achieves the same outcome (always store a memory) without requiring the LLM to comply. The fallback is a server-side guarantee, not a client-side obligation.

## Decision 7: Reject separate `store_memory` tool (Issue Solution D)
**Why**: The current architecture (spec 011, Decision 4) uses a single request → single tool call pattern. Adding a separate `store_memory` tool would require multi-turn tool call handling: the LLM calls `reflect`, the engine processes the response, then the LLM calls `store_memory` in a second turn. This adds significant complexity (state management, message history, second LLM round-trip) for a problem solvable with schema flattening + fallback.

## Decision 8: Update the system prompt to use flattened field names
**Why**: The system prompt currently says "Include a memoryEntry in your reflect response" — using the nested object name. After flattening, the prompt should say "Include memoryContent, memoryImportance, and memoryType" — using the flattened field names. The LLM needs to know exactly which top-level fields to populate. This is consistent with the schema-in-prompt philosophy (spec 010, though superseded by tool calling) — the prompt should match the schema.
