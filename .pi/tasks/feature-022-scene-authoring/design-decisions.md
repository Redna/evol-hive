# Design Decisions — Feature 022: Scene Authoring (Declarative)

## Decision 1: YAML as primary format, JSON Schema as validation backbone
**Why**: YAML is human-friendly for non-programmers (the stated audience in the issue). JSON is supported as a secondary format. The validation pipeline is "parse YAML → JSON object → validate against JSON Schema (Draft 2020-12)." This means the JSON Schema is the single source of truth for both YAML and JSON inputs.

**Alternative considered**: Define a custom DSL or TOML format. Rejected — YAML has the best balance of readability and ecosystem support (`js-yaml` is battle-tested). TOML is poor for deeply nested structures like affordance lists.

## Decision 2: No changes to SceneDefinition or loadScene
**Why**: `SceneDefinition` (in `packages/shared/src/types/world.ts`) and `loadScene` (in `packages/engine/src/assembly.ts`) already define the exact data model. The declarative format is a serialization layer on top — it maps 1:1 to the existing interface. This guarantees backward compatibility with all existing TypeScript scenes and tests.

**Impact**: Zero migration cost. Existing `coffee-shop.ts`, `morning-routine.ts`, etc. continue to work because they construct `SceneDefinition` objects directly.

## Decision 3: AffordanceHandlerPlugin pattern instead of convention-based auto-discovery
**Why**: The issue requests "register affordance handlers based on object types" and "support custom affordance handlers via plugin system." A `HandlerPlugin` interface (`{ objectType, handlers, preconditionCheckers }`) is explicit, type-safe, and testable. It avoids magic string conventions or dynamic imports.

**Alternative considered**: Auto-discover handlers by scanning a directory for files matching object type names. Rejected — too implicit, hard to debug, and doesn't work in bundled/compiled contexts.

## Decision 4: Refactor scene-helpers.ts into built-in plugins
**Why**: The handlers in `examples/scene-helpers.ts` (brew_coffee, sleep, read_book, go_to_*, etc.) are currently example-specific. To make `run-scene` work without user code, these handlers must be available as built-in plugins keyed by object type. The refactoring moves them into `@evol-hive/engine` (or a sub-module) as default `HandlerPlugin` instances.

**Backward compat**: `examples/scene-helpers.ts` can remain as a re-export shim or be updated to import from the new location. Existing tests that call `registerAffordanceHandlers(core)` are unaffected if the function signature is preserved.

## Decision 5: Doorway auto-generation in the loader, not in the schema
**Why**: In existing TypeScript scenes, doorway objects are generated by `makeDoorway(roomId, connections)`. In YAML, requiring users to manually write doorway objects for every room is tedious and error-prone. The loader auto-generates doorway objects when a room has `connections` but no doorway in its `objectIds`. This matches the `makeDoorway` pattern but removes the burden from the author.

**Alternative considered**: Make doorways a first-class schema concept with a `doorways: true` flag on rooms. Rejected — this would require changes to `SceneDefinition` (violates the no-change constraint). Auto-generation in the loader is transparent and produces standard `SmartObject` entries.

## Decision 6: CLI as a separate package (packages/cli/)
**Why**: The CLI needs to import from `engine`, `cognition`, `memory`, and `shared`. Placing it in a dedicated `packages/cli/` package follows the existing monorepo structure (ADR-0001). It gets its own `package.json` with a `bin` field for `npx evol-hive`.

**Alternative considered**: Put the CLI in the root `package.json` bin field. Rejected — the root package is private and doesn't have a build step. A dedicated package is cleaner and can be published independently if needed.

## Decision 7: js-yaml + ajv as the only new dependencies
**Why**: `js-yaml` is the standard YAML parser for Node.js. `ajv` is the standard JSON Schema validator. Both are mature, well-maintained, and have no transitive dependency concerns. They are added to `@evol-hive/shared` (for the schema) and `@evol-hive/engine` (for the loader), respectively.

**Alternative considered**: Use `zod` for validation instead of JSON Schema. Rejected — the issue explicitly asks for "validate against a JSON schema." Using a different validation library would not satisfy that requirement and would introduce a second schema definition to maintain.

## Decision 8: SceneValidationError with JSON Pointer paths
**Why**: When validation fails, users need to know exactly which field is invalid. JSON Pointer paths (e.g., `/rooms/0/objects/2/affordances/1/effects`) are the standard way to reference locations in a JSON document. `ajv` provides these paths natively. The error object includes the file path, all validation errors, and the raw parsed object for programmatic debugging.

## Decision 9: run-scene uses the same env-var pattern as coffee-shop.ts
**Why**: The existing `coffee-shop.ts` already supports `USE_REAL_LLM`, `LLM_BASE_URL`, `LLM_MODEL`, `USE_REAL_EMBEDDINGS`, etc. The `run-scene` CLI command reuses these same env vars for consistency. When `USE_REAL_LLM` is not set, a mock LLM is used so the command works offline for testing.

## Decision 10: create-scene is a guided wizard, not a full editor
**Why**: The issue asks for "interactive scene creation." A full TUI editor (like vim for scenes) is out of scope. Instead, `create-scene` is a step-by-step wizard using `@inquirer/prompts` (or `readline`): scene name → rooms → objects → agents → write file. The output is a valid `.scene.yaml` that passes `validate-scene`. Users can then hand-edit the YAML for advanced features (stateRules, compoundActions, etc.) that the wizard doesn't cover.

**Alternative considered**: Generate a template YAML and open it in `$EDITOR`. Rejected — too many environment assumptions. The wizard approach produces a valid scene immediately.
